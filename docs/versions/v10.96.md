## 二、真 bug 之一：XD 分类页恒返空（改版只改了一半）

### 现象

`/api/category?c=...` 对**所有**分类都返回 `{ok:true, items:[]}`。

### 排查（不看结论，看 HTML）

curl 直抓两份分类页对比 DOM：

| 页面 | 实际 DOM | `/game/` 出现次数 |
|---|---|---|
| `/sort/pcgame/`（新布局） | `span.type` + `a.tit` + `time.news` + `div.data`「评分：5.6 分」 | 264 |
| `/sort/dzmx/`（旧布局） | `a.soft-title` + `.list-ca` + `.dx` + `#stars` 星星宽度 | — |

抓取器写的是 `a.soft-title` ⇒ 在新布局页面上匹配 **0 次**，
`0 * 40 条 = 空数组`，**不报错**。

### 第一版修法是错的

「把选择器整体换成新的」⇒ 实测：

| 分类 | 修前 | 整体换新（错） | 双布局并存（对） |
|---|---|---|---|
| pcgame | 0 | **40** | **40** |
| host | 0 | 40 | 40 |
| mobile | 0 | 40 | 40 |
| dzmx | 0 | **0** | **24** |
| jsby | 0 | **0** | **24** |
| gj | 0 | **0** | **19** |

**修好 3 个、打死 3 个** —— 净效果等于「新增 3 个坏分类」。

### 改法

`fetchers/xdgamer.js::category()` 两套选择器并存，先新后旧，按 id 去重：

```js
const push = (o) => { if (!o || !o.id || seen.has(o.id)) return; seen.add(o.id); items.push(o); };
/* 布局 A（新） */
$('li:has(a[href*="/game/"]):has(a.tit)').each(/* span.type / time.news / 评分：x.x 分 */);
/* 布局 B（旧，细分分类仍在用） */
$('li:has(a.soft-title):has(a[href*="/game/"])').each(/* a.soft-title / .list-ca / .dx / #stars width */);
```

附两条硬约束：
* 新布局**没有体积字段** ⇒ `size: null`，不许拿旧字段猜（A 段有反向断言守着）。
* 新布局的「评分：0 分」视为**没有评分**（`> 0 ? Number : null`），旧布局用 `#stars` 的 `width%` 反推。

## 三、真 bug 之二：XD 搜索恒返 0 条（限流页伪装成 200）

### 现象

`/api/search?q=剑` 两个源，XD 永远 0 条 —— 而且**返回值与「真的没有这款游戏」完全一样**。

### 取证

把 XD 的响应体抓下来看：**1,755 字节**的一张提示页，正文

> 管理员设定搜索时间间隔为3秒，请稍后再试！

而它 `HTTP 200`、体积过了 `getHtml` 的 500 字节门槛 ⇒ 正常进 cheerio、正常解析、正常得到 0 条。
**全程没有任何一处会报错。**

另外测了三种请求头组合（无 Referer / 带站内 Referer / 带 Cookie）**全部拿回提示页** ⇒
不是鉴权问题，是站点级/IP 级限流。

### 改法

`LIMITED_RE = /管理员设定搜索时间间隔|搜索时间间隔/`
命中 ⇒ `sleep(3600)` 重试 **一次**（正好越过源站 3 秒阈值）⇒ 仍命中就 **`throw`**。

改后实测（2026-10-21 现测）：

```
xdgamer {"ok":false,"items":0,"error":"XD 搜索被源站限流（要求两次搜索间隔 3 秒），请稍后重试"}
jidi    {"ok":true,"count":2,"items":2,"error":null}
```

从「静默空」变成「如实报错 + 另一个源照常出结果」——
**用户至少知道该等 3 秒，而不是以为站里没这款游戏。**

## 四、顺带修：搜索缓存把失败锁了 5 分钟

`/api/search` 原来用固定 TTL。上一版（v10.95）刚在下载侧踩过同一个坑：**把一次失败缓存成了结论**。

`data/dl-cache-ttl.js` 新增 `searchCacheTtl(v)`：

| 情况 | TTL |
|---|---|
| 任一源 `ok:false`（有 error） | **45 秒** |
| 两源都成功 | 5 分钟（哪怕两源都是 0 条） |

★ 判据是「**有没有 error**」而不是「有没有条目」——
「搜索成功但确实没这款游戏」是真结论，照旧吃满 5 分钟，
否则每次输入都重打源站，更快触发源站限流（修 A 坏 B）。

`server.js` 两处（headless 分支 + 普通分支）都改成函数形态，
`test-v1096` C 段用反向断言守「不许退回写死毫秒数」。

## 五、噪声源：`/favicon.ico` 恒 404

全站 head 已内联 SVG icon，但部分浏览器仍会额外请求根目录 `/favicon.ico`。
每个页面都多一条 404 ⇒ **控制台里的真报错被这条噪声盖住**。

改法（放在 `express.static` **之前**）：

```js
app.get('/favicon.ico', (_req, res) => res.status(204).end());
```

204 才是正确语义：「我知道你在问什么，但这里没有」。
实测 204；UI 审计 K2「没有 404 资源」由红转绿。

## 六、端游资源新增「本体」分区

### 为什么不能像 MOD 那样预建索引

机地的「本体」链接只存在于**话题帖**里，只能按 tid 实时抓。
全量 17,220 款预抓 ⇒ 6 小时以上，且必然打成限流（v10.95 的 405 就是限流的产物）。

⇒ 只能做「**列表全量可见 + 卡内按需抓取**」。

### 形态

* 分区顺序：**本体 / MOD / 存档 / 修改器**，本体排第 1 且**默认落地**。
  理由：本体是「拿到这款游戏」的第一步，藏在最后等于没做。
* 列表走 `/api/jiditopics/list`，一页 24 张卡，搜索 + 排序 + 加载更多。
* 每张卡初始只有一个 **「🔍 查本体下载」** 按钮 —— **绝不自动抓**。
  24 张卡一次进页面 = 24 次机地请求，等于自己制造限流。
* 点一次 → `/api/download?url=…` → 取 `section === 'body'` 的条目 →
  按**帖**聚合成一行（一条 item 是一个盘口）、盘口按名称染色（夸克/百度/迅雷/阿里/123/蓝奏/UC/139/189/PikPak/其它）。
* 超过 3 帖 → 复用主站 `.dlpop` 弹窗壳（与详情页同一个壳，视觉一致）。
* 只重绘**这一张卡** —— 重绘整页会把滚动位置和已展开的卡全部复位。

### 本机缓存做第二层

抓到的结果按 tid 存 `localStorage`（key `gh.bd.links.v1`，上限 **400** 条，超限按 `ts` 淘汰最旧），
同一设备复访不重抓。服务端另有 30 分钟缓存、失败只缓存 60 秒（v10.95 的 `dlCacheTtl`）。

### 数字现测

| 项 | 实测 |
|---|---|
| 话题库总数 `/api/jiditopics/stats` | **17,220**（`hasCover` 17,220） |
| 页签数字胶囊 | 由接口回填，**不写死**（jsdom 拿不到时留「—」是正确降级） |
| 进页面时的下载请求数 | **0** |
| 点第 1 张卡 | 1 次请求 · 1,827ms · 3 帖 / 9 条链接 |
| 刷新页面 | 不重抓（读 localStorage） |

### 本轮自己犯的两个错（也是最有用的两条）

**① 改了几何不加断言 ⇒ 全量防线当场抓出 8 条**

给 `/resources.html` 加第四个分区后，我只改了 `test-resource-page.js`，
**忘了 `test-emulator-structure.js` 里还有一组断言也在查这页**。
全量一跑：8 条红 ——

| 断言 | 红的原因 |
|---|---|
| `.emu-bar-row` 共 6 行 | 变 8 行（每分区固定 2 行） |
| 恰好 3 个平级页签 | 变 4 个 |
| 页签顺序 `md,sv,tr` | 变 `bd,md,sv,tr` |
| 3 个可切换分区带 `data-et` | 变 4 个 |
| `ET_MAP` 覆盖 3 个分区 | 变 4 个 |
| `.res-tab` 类名 token 数 = 3 | 变 4 个 |
| `<title>` 文案 | 加了「本体」 |
| `bootTab` 默认 `'md'` | 变 `'bd'` |

★ **这不是"阈值放宽"，是分区数量真的变了** ⇒ 修法是把断言改成**新的精确值**，
不是把 `=== 6` 改成 `>= 6`。后者会让「以后漏删分区」永远不报错。
★ 顺带说明「**同一个产物被两个套件守着**」是常态 —— 改一处结构要**全局搜产物文件名**，
不能只改「名字对得上」的那一个套件。

**② 写注释 ≠ 登记：v10.95 的 32 条断言一条都没跑过**

`run-all.js` 的 SUITES 里，v10.95 的位置**只有注释没有数组项**：

```js
/* ★ v10.95：机地本体链接「为什么只显示 XD」… */
'test-v1096-audit-fixes.js',   // ← 注释下面直接接了下一版的条目
```

⇒ 覆盖性守卫报「`test-v1095-jidi-body-links.js` 未登记 —— 它永远不会被任何防线跑到」。
补上数组项后单跑 **32 / 32**。

★ 这正是「**新增套件必须登记 SUITES/BROWSER/COUNTERPROOF/SHIM**」那条铁律存在的理由：
**台账是数组、不是注释**，而人眼扫代码时注释和数组项长得一样。
