## 二、令牌：三个真实缺陷（都在前端）

线上逐端点实测（2026-10-20）：无令牌 `overview` 200、带令牌 `browse?admin=1` 200 —— **后端三通道鉴权是通的**，
问题全在前端表达：

| # | 现象 | 根因 | 改法 |
|---|---|---|---|
| ① | 保存后看不到令牌原文 | `saveToken()` 里 `$('tkInput').value = ''` | 保存后 `= tok()` 回填；加 👁 切 `type=password/text` |
| ② | 令牌填错也「保存成功」 | 只写 localStorage 就 toast | 保存时打 `/api/admin/verify`，绿/红当场给结论；失败时指示灯同步转红（不让绿点撒谎） |
| ③ | 令牌无效 = 空表格 | `api()` 只把 `needAuth` 塞进返回值，没有全局提示 | 任何 403 在内容区挂横幅，并区分「没填令牌」与「令牌不被接受」 |

新增 `GET /api/admin/verify`（**guarded**）：一个只回答「这张令牌算不算数」的探针。
它自己必须在护栏里，否则「有没有令牌」都返回 200，探针就失去意义（与铁律 161 同一个坑）。

## 三、资料覆盖层：`data/game-profile.json`（本轮唯一新增存储）

### 为什么不能回写爬虫产物

`data/games-*.json` 每天被 `daily-sync` 覆盖，人工值必然丢；而且覆盖层与原始值分开存才能回答
「这个字段是人改的还是抓来的」（`_prof` 标记），也才能一键清空回到爬虫值。

### 与既有两个文件的分工（同一语义只留一份实现）

| 文件 | 语义 | 影响面 |
|---|---|---|
| `game-notes.json` | 备注 | 纯标注，不影响任何逻辑 |
| `hide-overrides.json` | 可见性 | **行为**，影响列表 |
| `game-profile.json` | 展示字段 | 影响列表 / 详情 / 管理页展示 |

按**语义**分工而不是按页面分工：页面管理与游戏库写的是同一份文件的不同字段，
所以 POST 只接受 `patch`（整条覆盖会把另一个页面刚改的字段用旧值盖回去）。

### ★ 铁律：覆盖层只改「展示」，不改「匹配」

`apply()` 只在**输出**处调用（`withRes` 的**最后一步**、`/api/admin/game`、`/api/detail/merged`），
`gamesDb` 索引与 `resFor()` 全程看原始值。实战判据（`test-v1090` A15）：
`gameProfile.apply(o)` 的源码位置必须在 `resFor(g)` **之后** ——
提前叠会让「人工改个标题」直接打断已匹配的 MOD / 修改器 / 存档归属，**而且不报错，只是数字静默变少**。

### 字段与语义

| 字段 | 类型 | 备注 |
|---|---|---|
| `title` `cover` `url` `intro` `developer` `publisher` `releaseDate` | string | 页面管理改前 4 个，游戏库改后 5 个 |
| `hot` | number | 参与冷门口径（`hot=0` 且非新游 ⇒ 隐藏），改了会影响列表可见性 |
| `genres` `aliases` | array | 逗号分隔输入，落盘为数组 |

**空值 = 删除该字段的覆盖**（回到爬虫值），不是存空串。落盘用 `tmp + rename`：
半截 JSON 会让**整个文件**读失败，退回「无覆盖」远比丢数据更难查。

## 四、页面管理（新页）与游戏库（改造）

### 页面管理 · 爬取条目

| 项 | 实现 |
|---|---|
| 列 | 封面 42px / 游戏名 / 游戏ID / 平台 / 热度 / 更新 / 操作 |
| 行高 | 固定 56px（`.fxrow`），长标题单行省略 |
| 图片 | 真实 `<img class="cv" loading="lazy">`，加载失败隐藏而不是碎图 |
| 操作 | `查看` = 打开资料弹窗的**爬虫字段**形态 |
| 分页 | 上一页 / 附近 ±2 / 下一页 / 跳至第 N 页（回车即跳） |
| 数据 | `/api/library/browse?admin=1&cold=0`（冷门也看得见） |

### 游戏库 · 游戏资料

| 项 | 实现 |
|---|---|
| 列 | 封面 / 游戏名 / 游戏ID / 平台 / **资料 N/7** / 状态 / 备注 / 操作 |
| 资料弹窗 | 标题 / 封面 / 简介 / 类型 / 厂商 / 发行 / 发售日 / 别名 + 备注 + 可见性 |
| 完整度 | 7 项：封面、简介、类型、厂商、发行、发售日、别名（现算，不落库） |

### 表单语义：留空 = 用爬取值

输入框只回填**已有的覆盖值**，爬取值放 `placeholder`（`爬取值：…`）。
这样用户一眼能看出「这一项我改过没有」，也不会因为原样提交一次就把爬虫值冻成人工值。

| 模块 | 子源 | 条数（现测） |

| 问题 | 根因 | 改法 |

### 顺带修掉一个静默 bug：`browse` 从来没有 `q` 参数

⚠️ `gamesDb.search()` 返回的是**对象** `{q,count,items}`，取列表要 `.items`（铁律 148）。

## 六、资源覆盖（分类）与仪表盘（分模块）

### `GET /api/admin/coverage?module=base|mod|trainer|save`

```json
{ "module":"base", "total":19703, "covered":5811, "rate":29.5,
  "sources":[{"key":"fitgirl","label":"FitGirl Repack","matched":5811,"rate":29.5,"entries":5813,"builtAt":1792460139667}],
  "missingTotal":13892, "builtAt":1792460139667,
  "missing":[{"id":"jidi-171085167","title":"剑星","cover":"…","hot":348068}] }
```

- **分母 = 端游库全量（19,703）**，不是可见数 —— 冷门被隐藏不等于没有资源。
- **命中集合一律用各源自己的索引**（`fitgirl.RAW.byGame` / `resGroups.libIdsFor` / `tsmods.RAW.games` / `ensure().items`），
  **不逐款反查**：`trainers.byLib` / `saves.byLib` 是 O(n) 线性过滤，19,703 款逐个调会退化成 O(n²)（实测卡事件循环十几秒）。
- **缺口** = 该模块所有子源都没命中过的游戏，按热度降序取前 N。

### 仪表盘

顶部 chip：总览 / 本体 / MOD / 修改器 / 存档。选「总览」一次四张卡，选具体模块只请求那一个。
每张卡：覆盖率、缺口数、**数据时间**（该模块各子源 `builtAt` 的最大值）。

> 「爬虫可视化」不能只给条数：条数多但两周没更新，和条数少但天天新，管理动作完全相反。

## 七之二、防线自身的一处假数：`run-all` 取分（本轮附带修）

这一条不属于用户六条需求，但它决定了「用户看到的验证结论可不可信」，所以单独写。

| 现象 | 事实 |
|---|---|
| 全量合计 | 修前 `通过 10719 / 失败 -985`；修后 `通过 4649 / 失败 4` |
| 负数怎么来的 | `fail += (t - p)`，而某个套件被解析成 `p=6334 / t=5335` ⇒ 贡献 -999 |
| 谁被错认 | `test-v1089-admin-domains.js` 的明细行 `PASS 存档角标与列表同口径（6334 / 5335）`：以 `PASS` 开头、带一对大数字 |
| 为什么一直没发现 | 该套件真正收尾是 `结果：73 通过 / 0 失败`（数字中间夹「通过」），`\d+\s*\/\s*\d+` 匹配不上 ⇒ 一直走「倒着找最后一条 `n/m`」的退路 |
| 真危害 | **不是数字难看**：`-985` 的基础上多一条失败只会变 `-984`。也就是说**失败数这一栏彻底没有信息量，真红了也看不出来**（与铁律 108 同族，且这是它第二次复发） |

三个修法（`tools/run-all.js`）：

1. **明细行不参与取分** —— `PASS` / `FAIL` / `×` 开头的行直接跳过（**不含 `✅`**：有套件用 `✅ 42 通过 / 0 失败` 当收尾）；
2. **认 `n 通过 / m 失败`**（总数 = n+m）、`通过 n/m`、`n/m 通过`、`passed n/m` 四种写法；
3. **`t < p` 一律夹住并点名**（总数不可能小于通过数），不再把负值带进合计。

外加 `node tools/run-all.js --selftest-parse`：8 组**真实收尾样本**（含两次真凶原文），2 秒验完，
不用等 3 分钟全量跑 —— 这个坑已经复发两次，不能再靠人记。

> 顺带纠一个长期误读：修前那个 `10719` 不是「防线规模」，是被 `6334 / 5335` 之类明细数字**灌大的**。
> 真实规模是 **4,649 条断言 / 67 套**（与 v10.74 日志里的 4,626 同量级，可交叉印证）。

## 九、边界（如实写）

- **覆盖层只改展示**：改了标题/封面/热度/简介以后，搜索索引仍按爬虫标题建（`search` 走 `gamesDb` 原始值）。
  想让改动影响搜索，需要另做一轮「重建索引」——本轮**没有**做，也不假装做了。
- **线上 `data/` 每次发布被覆盖**：线上改的备注/豁免/资料覆盖不跨发布保留（设置页已写明）。
- **修改器模块只有两个子源**：GTrainers 有数据但没有扁平列表端点（只有 `byLib` 反查），
  加列表需要新端点，留到下一轮；覆盖统计里它**已计入**（`gt.ensure().items`）。
- **FitGirl 跨源错配仍在**：`xd-237「使命召唤1」` 挂着 MW4 的 repack（v10.89 起就能逐条看到），
  匹配算法要带反例集单独一轮，本轮未动。
