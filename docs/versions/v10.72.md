> 用户原话：「**如果我想直接通过下载按钮的话怎么样自动解压**」
>
> 用户补充（这一句才是真需求）：「**我的意思是自动判断链接是否是压缩包，以及压缩包解压后是否还有压缩包，并再次解压**」

## ③ 判定口径：**`sniffBuffer(head)` 是单一真源**（本版核心资产）

v10.71 已经有一份 `sniff(file)`（读文件头按魔数判压缩包）。本版要在**网络流**上做同一件事。

★★ **不能写第二份表。** 「文件版」与「网络流版」两份魔数表**必然漂移**（铁律 1 同族）——
漂移时会出现「落盘的时候认得出来、边下边判认不出来」这种**不报错**的分歧。

⇒ 抽成**按字节流的纯函数**，`sniff(file)` 退化成它的一个「读前 512 字节」外壳：

```js
/** 按魔数判定**一段字节流**是不是压缩包 —— 文件版与网络流版的**单一真源**。 */
function sniffBuffer(head) {
  if (!head || head.length < 4) return null;
  /* ★ 内部**自己截断**：head.toString('hex') 会按原长度再生成一份字符串 */
  const h = head.length > 512 ? head.slice(0, 512) : head;
  const hex = h.toString('hex');
  for (const m of MAGIC_TABLE) for (const sig of m.hex) if (hex.startsWith(sig)) return m.fmt;
  if (h.length >= 262 && h.slice(257, 262).toString('binary') === 'ustar') return 'tar';
  return null;
}
function sniff(file) { /* …readSync 512 字节… */ return sniffBuffer(buf.slice(0, n)); }
```

网络流侧要**多分两类**（网页 / 其它二进制），所以再加一层**只做分类、不做判定**的 `headKind`：

```js
/** 头部字节的**种类**判定（比 sniffBuffer 多分两类：网页 / 其它二进制） */
function headKind(head) {
  const fmt = sniffBuffer(head);
  if (fmt) return { kind: 'archive', fmt };
  const s = head.slice(0, 400).toString('utf8').toLowerCase();
  if (/^\s*<(!doctype|html)/.test(s)) return { kind: 'html' };
  return { kind: 'other' };
}
```

| 层 | 判什么 | 谁用 |
|---|---|---|
| `sniffBuffer(head)` | 是不是压缩包、是哪种 | 唯一真源 |
| `sniff(file)` | 同上，输入换成文件 | 解压链路（v10.71） |
| `headKind(head)` | archive / html / other **三分类** | **下载链路（本版）** |

## ④ 实现（三段改动）

### 4.1 `data/extractor.js` —— `downloadTo` 加**头部早期判定**

新增选项 `expectArchive`。判定**边收边做**，头部满 512 字节即定种类：

```js
let headBuf = Buffer.alloc(0); let headV = null;
const judge = (final) => { if (headV) return headV;
  if (headBuf.length >= 512 || final) headV = headKind(headBuf); return headV; };
let early = null;
for await (const chunk of r.body) {
  chunks.push(chunk); got += chunk.length;
  if (headBuf.length < 512) headBuf = Buffer.concat([headBuf, chunk]).slice(0, 512);
  const v = judge(false);
  if (v && v.kind === 'html') { early = bail('返回的是 HTML 页面而不是文件（需要登录/中间页）', { notArchive: true }); break; }
  if (v && v.kind === 'other' && opts.expectArchive) { early = bail('这条地址返回的不是压缩包（Content-Type: …）', { notArchive: true, sniffed: 'other' }); break; }
  if (opts.maxBytes && got > opts.maxBytes) { early = bail('超过大小上限 …'); break; }
  if (opts.onProgress) { try { opts.onProgress({ got, total }); } catch (e) {} }
}
if (early) return early;
```

★ **`break` 而不是 `return`** —— 见坑 ②，这是本版最贵的一处。
★ 命中后**一个字节都不落盘**：`chunks` 只活在内存里，`early` 直接返回。
★ 正常落盘路径的返回值里加 `sniffed`（用同一把尺子再判一次落盘结果，顺带证明两条路一致）。

### 4.2 `server.js` —— 任务态 + 一个带护栏的 `open`

任务对象新增三项（`exNewTask`），并在 `exSnapshot` 里带出：

## ⑤ ★★ 踩的坑（四条，两条是我自己埋的）

### ① ★★ `got <= 400` —— v10.71 的 HTML 早判**被整个跳过**（既有 bug，顺手修掉）

v10.71 写的是：

```js
if (got <= 400) { /* …判是不是 HTML… */ }      // ← 错
```

只要**首个 chunk 就大于 400 字节**，那次判定被**整个跳过**，HTML 中间页会一路下完才暴露
—— 用户看到的是「下了一整页然后说不是压缩包」。

★ 根因是**判据的作用域写窄了**：把「累积到 400 字节再判」写成了「单次 `got` 不超过 400 才判」。
修法：改成**累积 `headBuf` 到 512 字节再判**（跨 chunk 累积，与 `sniffBuffer` 同一把尺子）。
★ 这条**既有断言全绿** —— 因为当时没有任何一条断言在喂「首 chunk > 400 字节」的响应。
本版 `test-v1072-download.js` 专门起了个 **`/html-big`** 端点（单 chunk 就给 1KB HTML）钉住它。

### ② ★★★ `abort` 在循环内调用会**吞掉结论**

第一版提前止损写成「在 `for await (r.body)` 循环内部 `ctl.abort()` 然后 `return`」。
e2e 的 B 场景实测得到：

```
state=error   error=This operation was aborted     ← notArchive 标记整个丢失
```

★ 机制：`abort()` 让**正在被迭代的那个流**抛 `AbortError`，**异常比 `return` 先到外层 `catch`**
⇒ 我们精心准备的 `notArchive: true` 被一句含糊的「This operation was aborted」盖掉，
前端只能显示「下载失败」，**用户根本不知道是「这条地址不是压缩包」**。

⇒ 修法：**循环内只 `break`，循环外统一返回**。
★ 判据：`notArchive` 这个语义标签的**唯一出口**必须是函数返回，不许走异常路径。

### ③ ★★ 提前止损的判据**只能来自服务器**

「我提前断了」这件事，**客户端自己说是证明不了**的（客户端可能只是本地读取出错）。
能当证据的只有服务端：客户端主动 `abort` ⇒ 服务端 `res.writableFinished = false`。

⇒ 防线里专门起了 **`/html-slow`** 端点（慢速吐一段大 HTML）配合
`slowState.closedEarly` 断言：**实测 `closedEarly=true` / 服务器是否吐完 = false**。
★ 这才叫「证明它真的提前止损了」，而不是「证明我的代码里有个 `break`」。

### ④ ★★ 顺手照出**一个防线假绿 + 一个防线机制缺口**

- **假绿**：`tools/test-v1071-extract-counterproof.js` 本轮实测是 **`❌ 反证失败 1 项`** 的，
  而上一轮全量报的是「**3995 / 0**」。
  根因：**取汇总正则没跟着产物格式改** —— v10.71 把套件收尾统一成「通过 n/m（失败 f）」
  （**斜杠后是总数**），而该反证的 `SUM_ALL_GREEN` 还是旧的「通过 n / 失败 f」⇒ **恒不匹配**
  ⇒ 「还原后**必须全绿**」那一步判据**整个失效**。
  ★ 修法：`const SUM_ANY = /通过 \d+ \/ \d+（失败 \d+）/;` +
  `const SUM_ALL_GREEN = /^通过 (\d+) \/ (\d+)（失败 0）$/;`（**跟着格式改，不是放宽**）
  ⇒ 修后 **87 / 87（失败 0）+ `✅ 还原干净`**。
- **机制缺口**：★★ **`tools/run-all.js` 的 `COUNTERPROOF` 表只「校验」、从不「执行」**。
  所以**反证失败在全量防线里是看不见的** —— 上面那条假红就是这么活了整整一版。
  ⇒ 本版在 run-all 的注释里**如实记下这个现状**（不假装它被守住了），并把它补进 PITFALLS。

### ⑤ 其它三条（小，但都花了时间）
