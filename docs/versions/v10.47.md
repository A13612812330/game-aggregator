## 一、改了什么

### ① 三个分区统一卡形：一卡一款游戏（不再一卡一条）

`MOD` / `存档` / `修改器` 原先各是「一卡一条」，条数从几千涨到两万多后列表已无阅读性。
改为**一种卡形三个分区共用**（`article.emu-card.grp`）：卡内铺**前 3 条**可下载条目，
超出部分由卡内「展开全部 N 条」**原地**铺开（不跳页、不换弹窗）。

| 口径 | 值 |
|---|---|
| 网格列宽 | 248 → **316px**（条目行要同时放「序号 + 标题 + 通道按钮」，248px 下标题只剩 6~7 字） |
| 组卡封面高 | 92 → **78px**（主体信息在卡内列表，封面只做识别；留 92px 会一屏看不到两组） |
| 卡内明文 | **前 3 条**（`PREVIEW = 3`，服务端 `slice`） |
| 展开上限 | 300 条（赛博朋克2077 单组 717 条，一次全铺会撑爆 DOM） |

三个分区的差异**全部收在 `GRP_META` 一张表**里（标题 / 排序项 / 统计口径 / 来源徽标顺序），
渲染器只有一份（`grpCard` / `glRow` / `bindGrpGrid` / `loadGrp` / `initGrp`），
入口仍是 `initMd` / `initSv` / `initTr`（生成器按这些名字调用）。

### ② 存档分区只出「真有可下载存档」的游戏

不再出 Ludusavi「存档位置库」的卡片 —— 位置回答的是「放哪」，与「去哪下」是两件事，
混在一页里用户分不清哪个能点。位置线只在**详情页的「📍 存档位置」二级弹窗**保留。

### ③ 详情页两块卡片：只展示存档 + 高度收到 3 行

- `--d-rows` **5 → 3**（用户拍板「更紧凑：预留行数 5 → 3」）；两块共同基准变矮，等高诉求不变。
- 详情页**存档块**同口径改形：旧版读 `/api/saves/match`（Ludusavi 路径），**一个文件都下不了**，
  与 v10.46 已改过的合并弹窗口径不一致；现读 `/api/res/game`（游侠 + GTrainers 可下载条目）。
- 两块提示仍是**显式三行**（各 2 个 `<br>`），文案随口径更新；
  「`<code>` 包占位符」「存档前先退出游戏」随位置线**搬进 `svLocHtml`**（#svLoc 弹窗），没丢。

### ④ 新增两个「有真下载链」的源（按游戏名匹配）

| 源 | 板块 | 拿到的链 | 说明 |
|---|---|---|---|
| **GTrainers** | 存档 `savegames` / 修改器 `trainers` | **真实文件直链**（301 后 Location，免登录） | 纯 HTTP 可直连（uCoz/DLE `load` 模块） |

## 三、踩过的坑与根因

### 1. ★★ `GRP_META` 键名重复 ⇒ 排序项从来没渲染过（静默覆盖）

三个分区的对象字面量里 `sorts` 写了**两次**：先 `sorts: 'mdSorts'`（容器 id），
后 `sorts: [[...]]`（排序项数组）。JS 里后者**静默覆盖**前者，于是
`document.getElementById(meta.sorts)` 收到的是**数组**、恒返回 `null` ⇒
三个分区的排序按钮**一次都没生成过**，且不报任何错。

> 根因不是「写错一个字」，是**同一个键被塞了两种东西**。已在 `PITFALLS.md` 铁律 42 记档。
> 修法：容器 id 改名 `sortsBox`。抓到它的是 `test-resource-page.js` 的
> 「3 个 `.emu-sort`，第一个默认 on」—— 这条断言在改形时顺手补上，正好接住了。

### 2. GT 分页形式写错 ⇒ 静默少数据（文档漂移）

`fetchers/gtrainers.js` 文件头的「站点结构」写着 `<catid>-1-<page>`，而正文长注释写的是
`<catid>-<page>-1`。**正确是后者**：写成前者时 `p≥50` 之后会**回吐同一页且 HTTP 200**，
静默只剩几百条。已统一并对齐警示，脚本内还有「平均每页条数」完整性自检兜底。

### 3. FR：CF 按**速率**限流，不是按总量

| 实测（2026-10-10，三轮） | 结果 |
|---|---|
| 并发 3 + gap 150ms | 336 页**挂 276 页** |
| 并发 2 + gap 260ms | 40 页挂 3 页（失败原因清一色 `CF 挑战（429）`） |
| **并发 1 + gap 400ms** | 40 页 **0 失败** |

⇒ 串行 + 400ms（≈0.77 req/s）是换来「一页不丢」的代价；退避也要够长
（3s/6s/12s 乘性 + 抖动 + 尊重 `Retry-After`，1.2s/2.4s 那种量级**恢复不了**）。

### 4. ★★ FR 长跑崩在 `detached Frame` ⇒ 36 分钟全废

Tables 板块 336 页跑完、进 Trainers 板块时崩在 `Attempted to use a detached Frame`。
两个原因叠加：
① 崩的那行是「板块**首个**请求」，**在重试循环之外**，没有任何保护；
② 更根本 —— detached Frame 是**浏览器侧上下文失效**（不是 CF、不是限速），
   **在同一个 frame 上重试 evaluate 永远是同一个错**，必须 `page.goto` 回本域名拿新的 execution context。

修法：① 抽出 `withRecover`，识别 detached / context destroyed ⇒ 恢复页面上下文再重试（5 次）；
② 三个调用点（含板块首个请求）全部走自愈版；③ 加**板块级增量落盘**并打 `partial: true`，
读缓存路径**拒绝**中间态（否则半份缓存会被当成完整列表用，静默少一半）。

### 5. 「裸 CSS 文本」断言被**数据**撞红（判据太宽）

反证时抓到 `.0 {FLiNG}` —— 那是 GTrainers 修改器标题里合法的署名
（`… v1.0 {FLiNG}`），不是 CSS 泄漏。原判据 `[.#]\w+\s*\{[^}]*\}` 把数据里的花括号也算进去了。
**修法是收窄判据、不是删断言**：真 CSS 声明块里必有 `属性:值` ⇒ 加上「括号内须有冒号」；
配套做了正反双向自检（3 例应放过 + 3 例应命中，全过）。

### 6. ★★ 反向断言只查派生页、不查主源（反证暴露）

`test-emulator-structure.js` 的「旧卡面样式整组已删」第一版只看 `res`（派生页）。
反证时往**主源**加回 `.emu-card .sv-open{…}` —— 断言照样 **PASS**
（没重建派生页，`res` 里当然还是没有）。可**主源才是唯一编辑入口**：
下一个人改了主源又碰巧重建，旧样式就回来了，而这条「已删」断言在重建前一直是绿的。
⇒ 改成主源与派生页各查一遍。**这是本轮反证唯一的「打坏不变红」**，也是最值钱的一条。

### 9. 「文档写了口径」≠「工具按口径算」（收尾时新发现）

`ROADMAP.md` / `WORKFLOW.md` 都声明「KB = **磁盘字节** / 1024」，而复现命令
`tools/_probe-doc-numbers.js` 自己用的是 `s.length / 1024`（**字符数**/1024）——
四页里有大量中文，两者差得很远：

| 文件 | 字节口径（文档声明的） | 字符口径（探针实际用的） | 差 |
|---|---|---|---|
| `index.html` | **417 KB**（JS 251 / CSS 154） | 326 KB（JS 187 / CSS 130） | **91 KB** |
| `emulator.html` | 480 KB | 377 KB | 103 KB |

这与 v10.32 / v10.38 记的「同一个文件出现过三个不同的 KB 数」是**同一个病**：
**口径只写在纸上，没人验过工具真的按它算**。修法：探针改成 `Buffer.byteLength(x,'utf8')`
+ `fs.statSync().size`，并补上原先**漏掉的 `resources.html`**（v10.44 新增页，探针清单没跟上）。
★ 顺带一个自伤：第一次给这段加注释时写了「`**字符数**/1024`」，
其中星号紧跟斜杠构成了块注释的**提前闭合序列**，探针直接 `SyntaxError` ——
正是本项目 PITFALLS 里记过的那条（**块注释/模板串里不许出现提前闭合序列**）。

### 10. ★★ FR 全量抓到 33 分钟时**静默挂死**：无限重试 + 进度不可见

第一次全量列表跑到 33 分钟时，进程表现为：**0% CPU · 无 TCP 连接 · 无子进程 · 80 分钟无任何落盘
—— 但一直「在运行」**。外部完全看不出它是卡了还是在抓。根因三条叠加：

| # | 缺陷 | 后果 |
|---|---|---|
| ① | `recoverFrame()` 写成 `page.goto(...).catch(()=>{})` | **吞掉失败、返回 `undefined`** ⇒ 调用方无法区分「恢复了」与「浏览器已死」 |
| ② | 没有全局熔断 | `withRecover` 5 次 × 外层每页 4 次 ⇒ **无限循环**，既不产出也不退出 |
| ③ | 日志只有「板块开始 / 板块结束」两行 | 页级无进度 ⇒ **卡死与在跑长得一模一样** |

修法（三条都是「让它响亮失败」，不是「让它别失败」）：
① `recoverFrame()` 返回**布尔**（判据 = 能否拿到 title）；② 连续 `--ctx-dead`（默认 6）次恢复失败
⇒ 抛「浏览器上下文不可恢复」终止；③ **页级进度**（`[table] 12/336 页 · 52 帖 · 15s`）；
④ 顺带给 `page.evaluate` 加**硬超时**（页面内 `fetch()` 本身没有超时，CF 挂住就永不返回）。

★ 复现与验证：`--list-only --max-pages 5` 在**旧代码**上正好复现「5 次恢复失败后无限循环」；
新代码上同一命令**当场抛错退出**（不再挂）。

### 11. ★★ page 上下文死掉后 `page.goto` **救不回来** ⇒ 只能换 page

实测：**跑完一个板块、切到下一个板块时 page 上下文必死**（`Attempted to use a detached Frame`），
而 `page.goto` 回本域名**也恢复不了** —— 因为 detached Frame 是**浏览器侧那个 frame 已经没了**，
在死对象上做任何操作（包括 goto）都落在同一个死对象上。

修法：**弃掉旧 page、`browser.newPage()` 开新的、重新过挑战**。代价很小 ——
profile 里已有 `cf_clearance`，实测第二次过挑战只要 **1.9s**。修完后同一命令（`--max-pages 5`）
两个板块全部跑完、**失败页 0**。

### 12. ★★ CF 是**按会话**收紧的：不要在一轮里反复起停脚本

跑完列表后，我连续起了三次 `--max 60` 做速率标定 —— **第四次直接过不了挑战**
（`title` 停在「请稍候…」，80s 到顶）。profile 里的 `cf_clearance` 不再够用。
⇒ 这三轮的耗时（各 82s）**全是挑战超时的 80s，不是抓取耗时**，由它算出来的「1366ms/条」是**无效数字**。

**教训**：这类「挑战 + 长跑」的源，**一轮跑够**，别反复起停；标定速率要用**当轮真实完成**的计数
（阶段① 的 `528.2s / 433 页` 才是有效值）。
