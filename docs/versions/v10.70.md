### 2.4 ★★ 排序依据显性化（学 XDGAME「行尾写依据值」）

XDGAME 每行末尾直接写「574,032 热度」「2,141 赞」「10 分」「554 GB」；机地写「7.9W」；byrut 写下载数。
⇒ 我们按**当前排序维度**在行内显示该维度的值。**排序键 ↔ 显示键必须在同一处定义**：

```js
function sortKeyPill(it, okScore) {           // ★ 唯一定义处
  if (curSort === 'hot') { const h = fmtHot(it.hot); return h ? `<span class="pill hot">🔥 ${h}</span>` : ''; }
  if (curSort === 'size' || curSort === 'sizeAsc') return it.size ? `<span class="pill size">${esc(it.size)}</span>` : '';
  if (curSort === 'score') return okScore ? `<span class="pill score">★ ${it.score}</span>` : '';
  if (curSort === 'updated') return '';       // ★ 见下面 3 条口径
  return '';                                  // title：名称排序没有「值」可显示
}
```

三条踩过的口径：

1. **`updated` 视图不显示日期依据值** —— 列表本来就按日期分组，每组上面已有 `.date-sep`
   分隔条；行内再顶一枚日期 pill 是**同一信息说两遍**，还会把日期挤到标题左边（第一版就这么错的）。
2. **座垫式防重**：`size` 视图下容量 pill 既是依据值、又会作为常规字段出现 ⇒ 会出**两枚一模一样**的。
   ⇒ `if (it.size && curSort !== 'size' && curSort !== 'sizeAsc')`。
3. **`fmtHot()` 统一热度口径**（学机地「7.9W」）：≥10000 → `34.8 万`（≥100 万取整）；否则 `8,742` 千分位。

## ③ ★★ 技术核心：排序口径**只此一份**

扩维度不难，会出事的是**口径分裂**。本轮修掉两处：

### 3.1 两份 `keyOf` ⇒ 一个 `cmp(sort)`

`server.js` 的 `/api/library/browse` 在 `scope=pc` 走 `gamesDb.browse()`，
而 `scope=mob|all` 走**内存排序**（`mobPool.sort` + `mergePick`）—— 那里历史上另写了一份 `keyOf`。

> 两份口径一旦漂移，同一个 `sort` 参数在两个 scope 下会排出不同顺序，
> 而且**不报错、测试也照绿**（当时没有任何一条断言在比两个 scope 的顺序）。

⇒ 抽出 `gamesDb.cmp(sort)`，三处共用。**注意它返回的是比较函数、不是取值函数**：

```js
const SORT_KEYS = ['updated', 'hot', 'score', 'size', 'sizeAsc', 'title'];
function cmp(sort) {
  const k = SORT_KEYS.includes(String(sort || '')) ? String(sort) : 'updated';
  return (a, b) => { ... };
}
```

★ 为什么不能是取值函数（`keyOf`）：`sizeAsc` / `title` 需要**「小于」方向**，降序取值函数表达不了。
同理 `mergePick` 的 `keyOf(A) >= keyOf(B)` 只能表达降序 ⇒ 改成 `cmp(A[i], B[j]) <= 0`。

### 3.2 白名单也不能写死两处

`server.js` 原本是 `['score','size'].includes(...)`。加维度要改两处，**漏改一处 = 前端发了 `hot`、
服务端静默回落 `updated`**（用户看到按钮高亮变了、列表没动，还不报错）。
⇒ 改成 `gamesDb.SORT_KEYS.includes(...)`，单一来源。

### 3.3 ★★ `sizeAsc`：容量**无效**的条目必须排最后

无效有两种，且**实测都存在**：

| 情形 | 来源 | 全库条数 |
|---|---|---|
| ① `sizeGb()` 返回 `null` | `size` 为空串 / 解析不出 | 含在 480 内 |
| ② 解析出来是**数值 0** | 源站声明 `"0.0GB"` / `"0KB"` | 含在 480 内 |

只判 `null` 会让 ② 被当成「最小容量」**冲到最前** —— 榜单第一页变成「数据缺失榜」
（实测前 8 名全是 0）。而直接写 `null - n` 更糟：算成 0，同样冲到最前。

```js
const zA = sizeGb(a.size), zB = sizeGb(b.size);
const okA = zA != null && zA > 0;      // ★ > 0 是必需的，不是防御性写法
const okB = zB != null && zB > 0;
if (!okA && !okB) return tie();
if (!okA) return 1;
if (!okB) return -1;
return (zA - zB) || tie();
```

**修后全量校验**（`tools/_probe-v1070.js` 探针 + `test-v1070-sort-keys.js` 全量扫描）：
有效段 19,051 条**单调不减**，无效段起点恰好 `index=19051`，**越界 0 处**；
第 1 名是 `1MB`（数值 0.001 GB）而不是 `0.0GB`。

## ④ 顺手修掉的横向溢出（761–1060px 区间）

**发现方式**：跑完整防线时 `test-search-ui.js` 有一条红 ——
「820px 视口无横向溢出（抽屉 680 < 100vw）」实测 `831 ≤ 820` 为假。

**定位**（`tools/_probe-v1070-overflow.js`）：`#colMain` 宽 **809**、`left=22` ⇒ `right=831`。

**根因是一处写法错误，不是本轮引入的**：

```css
.grid2{grid-template-columns:minmax(0,1fr) 340px;...}       /* 桌面档：min=0 ⇒ 不会被撑破 */
@media(max-width:1060px){.grid2{grid-template-columns:1fr}} /* ★ 单列档：1fr ⇒ min=auto=min-content */
```

`1fr` 展开是 `minmax(auto,1fr)`，`min` 取 **auto = min-content** ⇒ 栅格项的 min-content 会把列**撑宽**。
`≤760px` 那档另有 `#colMain{min-width:0}` 兜着，`>1060px` 写的是 `minmax(0,1fr)` ——
**只有 761–1060 这段两头都不管**（与 v10.68 修的 `.live-tag` 溢出是**同一类**「断点区间漏兜底」）。

**取证过程**（★ 两次假设都被数据推翻，所以结论可信）：

| 步骤 | 做法 | 结果 |
|---|---|---|
| A/B① | 页面上临时把排序 pill 从 6 个减回 3 个（v10.70 前的档数） | docW 仍 831 ⇒ **pill 数不是触发因素**（我的第一个假设错了） |
| A/B② | 页面上临时给 `#colMain` 加 `min-width:0` | `#colMain` 809→**768**、docW 831→**812**、**内部越界元素 0 个** ⇒ 机制确认 |
| 版本 A/B | 把 `git show HEAD:public/index.html` 临时挂到 `/_head-probe.html` 实测 | HEAD 版 docW **932** / `#colMain` **910** / 越界 **312** 个 |

★ **结论：这是历史遗留**（`1fr` 写法自 v10.14 初始提交 `bfcef54` 就在），
而且 **v10.70 已经把溢出自 932 压到 831**（本轮缩略图 96→78、删掉行内长英文名，都减小了 min-content）。

**修法**（一个词）：`1fr` → `minmax(0,1fr)`。
修后 820px 下 docW **812**、`#colMain` **768**、越界元素只剩那个 `position:fixed` 的抽屉（不贡献文档宽）。
`test-search-ui.js` 由红转绿（47/47）。

★ 顺带把**这一档视口**纳入首页几何套件：`test-home-fold.js` 从 2 档扩到 **3 档**（+`平板 820×900`）。
理由：本页的响应式分档是 `≤760` / `761–1060` / `>1060`，
**再加一个 1440 或 390 的视口永远测不到中间那档的问题**，必须钉住这个**区间**里的一个点。

   结果整套件 **FATAL** —— 首页脚本里 `$('#jidiBtn').addEventListener(...)` 拿到 null ⇒
   **整页脚本挂掉** ⇒ 所有浏览器断言都无法进行（红 0 条、无汇总行）。
   那证明的不是「F5 有效」，而是「首页脚本对按钮缺失不健壮」（另一个话题，本轮不动）。
   ⇒ 改成「隐藏按钮」，精确命中 **F6**（可见性）而 **F5**（在 DOM 里）仍绿 —— 这正是想要的精度。

## ⑥ 铁律（已写入 `PITFALLS.md` 94–101）

**94 · 口径「单一来源」要落在**返回比较函数**上，且白名单也算口径。**
两份 `keyOf`（`browse` 路径 vs 内存排序路径）漂移时**不报错、测试也照绿**；
白名单写死两处则「前端发了新参数、服务端静默回落」。⇒ 比较函数从数据层出去、白名单引用同一个 `SORT_KEYS`。

**95 · 「无效值」必须和「零值」分开判。** 源站缺值常声明成 `"0.0GB"` / `"0KB"`，解析出来是**数值 0**；
只判 `null` 会让它冲进「最小」那一端，榜单第一页变成「数据缺失榜」。判据是 `v != null && v > 0`。

**96 · 排序依据值的显示键必须与排序键同处定义。** 分成两处就会出现「按 A 排、显示 B」，
而且**不报错**（两份都各自正确）。

**97 · 阈值「跟着改版收紧」是每轮必做项，不是可选优化。** 本轮 hero 从 275 压到 197，
而旧闸是 340 —— **「退回 275」在本套件里是绿的**。不收紧 = 防线对该回退失效。

**98 · 每加一个取样视口/档位，阈值必须先量再定。** 照搬相邻档的阈值 ⇒ 窄档余量被吃光、
当场假红（本轮 820 档照抄桌面档，首卡 top 603 > 600 直接红）。

**99 · 反证要「打了才知道红在哪一条」，且靶子不许引发级联崩溃。**
前者：patch 只坏一半时，暴露的可能是**另一条**断言（本轮 A：预期 D1、实际 D7）。
后者：删 `id` 可能让整页脚本挂掉（红 0 条 + 无汇总行），那不是反证成功、是反证失败
⇒ 必须额外断言「套件仍能跑出汇总行」。

**100 · 断点区间是「两头都不管」的重灾区，取样要覆盖区间中点。**
本页分档 `≤760` / `761–1060` / `>1060`，v10.70 修掉的横向溢出**只存在于中间那档**
（`≤760` 有 `min-width:0` 兜底、`>1060` 写的是 `minmax(0,1fr)`）。
再加一个 1440 或 390 的视口**永远测不到它**。同类：v10.68 的 `.live-tag`（761–845）。

**101 · `1fr` ≠ `minmax(0,1fr)`。** `1fr` 的 `min` 是 `auto`（= min-content）⇒ 栅格项会被内容撑宽。
要「允许收缩」必须显式写 `minmax(0,1fr)` 或给子项 `min-width:0`。
本轮 `@media(max-width:1060px)` 那条自 v10.14 起就写错了，一直没人发现
—— 因为**溢出量取决于内容的 min-content**，内容一变宽就爆出来。
