# v10.112 筛选三处真修：冷门开关解耦 + 后台死控件 + 前端列表搜索

> 2026-10-23 · 用户原话：

这一版没有新功能，只有**实测出来的三个 bug**。三个的共同特征：
**页面照常打开、不报任何错、按钮也在，但点了等于没点**。

修之前先把「是不是真 bug」量出来，不吃「看起来像 bug」：

|---|---|---|

## 1. bug ① 后端：冷门剔除把三个筛选一起掐了

### 改前

```js
if (isAdminView && !o.excludeCold) {
  const conds = [];
  if (hv === '1') conds.push(g => coldHide.isHidden(g) === true);
  ...
}
```

`hidden` / `asrc` / `note` 三个管理侧筛选**只在 `cold=0` 时才生效**。

为什么以前没炸：后台的 cold 开关是死控件，永远发 `cold=0` ⇒ `excludeCold` 恒为 false
⇒ 这个条件恒真。**两个 bug 互相掩盖**，只要修好其中一个，另一个立刻显形。

### 实测证据（改前，同一台 8123）

```
cold=0                  19766
cold=1                  12308
cold=0&hidden=1          7458
cold=1&hidden=1         12308   ← 与 cold=1 完全一样 = 筛选被吞
cold=0&asrc=jidi         3699
cold=1&asrc=jidi        12308   ← 同上
cold=0&note=1               0
cold=1&note=1           12308   ← 同上
```

### 改法

```js
if (isAdminView) {
```

「池前剔除冷门」是一个开关，「附加条件」是另一件事，两者不该互相开关。

### ★ 连带必须解的一个冲突：`hidden=1` 与「剔除冷门」互斥

修完 ①，后台真的会发 `cold=1` 了，于是：

- 池前剔除冷门 ⇒ 把所有 `isHidden` 的行**删光**
- `hidden=1` ⇒ 只留 `isHidden` 的行

两者相加 **必然 0 条**。管理员一点「仅隐藏」就是空列表，看起来像功能坏了。

所以加了让位，且**只在 admin 视图内**（否则公开接口加个 `hidden=1` 就能绕开冷门隐藏，
等于把「无人问津自动隐藏」直接废掉）：

```js
if (isAdminView && String(req.query.hidden || '') === '1') o.excludeCold = false;
```

### 实测（改后）

```
cold=0                  19766
cold=1                  12308
cold=0&hidden=1          7458
cold=1&hidden=1          7458   ← 让位生效，同一批「隐藏行」
cold=0&asrc=jidi         3699
cold=1&asrc=jidi         1269   ← 真生效了
cold=1&asrc=xd          11039   ← 1269 + 11039 = 12308 ✓ 自洽
cold=1&hidden=0         12308
```

两个恒等式都成立：`1269 + 11039 = 12308`、`7458 + 12308 = 19766`。
这不是「跑通了」，是**口径互斥且完备**。

## 2. bug ② 后台：「🌙 显示冷门」是纯装饰控件

### 改前

```js
if (!showCold) p.set('cold', '0'); else p.set('cold', '0');   // 两分支一模一样
```

```js
function toggleCold() { showCold = !showCold; $('cCold').classList.toggle('on', showCold);
  toast(showCold ? '冷门行已显示（筛选中标注）' : '冷门行仍全部列出，仅切换高亮'); }
```

三个毛病叠在一起：

1. 请求永远发 `cold=0` ⇒ 勾不勾都是全量；
2. `toggleCold` **不 reload**（`toggleGroup` / `toggleNote` 都有）；
3. toast 写着「仅切换高亮」，可代码里**没有任何高亮逻辑**（`g.cold` 的 🌙 徽标一直渲染，
   与 `showCold` 无关）。

### 改法

```js
p.set('cold', showCold ? '0' : '1');
```

语义对齐控件名：不勾 ⇒ 剔除冷门（与前台同口径）；勾选 ⇒ 全量。

```js
function toggleCold() {
  showCold = !showCold;
  $('cCold').classList.toggle('on', showCold);
  offset = 0; reload();
  toast(showCold ? '已含冷门行（全量口径）' : '已隐藏冷门行（与前台口径一致）');
}
```

### 实测（浏览器真点，`tools/_shot-v10112.js`）

| 操作 | `#gInfo` |
|---|---|
| 默认（不勾） | 共 **11,728** 条 |
| 勾上「🌙 显示冷门」 | 共 **18,751** 条 |
| 冷门显示态 + 「仅隐藏」 | 共 **7,371** 条（改前必然是 0） |
| 冷门显示态 + 来源=机地 | 共 **3,698** 条（改前等于全量） |

后台数字比接口小（11,728 vs 12,308）是因为列表默认 `group=1` 同款合并 —— 不是口径不一致。

## 3. bug ③ 前端：列表内没有搜索，「在结果里再缩小」做不到

后端 `/api/library/browse` 从 v10.90 起就支持 `q`（当时的注释写着「管理页的搜索框一直在发 q」），
但**前台列表从没发过** —— 前台唯一的搜索是顶栏那个跨四库实时查源站的弹窗。

两种诉求不是一回事：弹窗是「我不知道它在哪，帮我找」；列表搜索是「我已经筛好了，再收窄一格」。

### 改法

- `.cat-panel` 里加一行「搜索」（与分类行同一操作台，不另起面板）
- `curQ` 与 `curCat` / `curSort` / `curSize` / 五个开关**全部叠加**
- 防抖 320ms（中文输入法拼字阶段 `oninput` 会连发十几个事件）
- 搜索态**不按日期分组**（命中集散落在各天，分日期只会打散结果）
- 空态换成搜索语（`没有找到「xxx」`）而不是「当前筛选下暂无收录」——后者在搜索语境下是假话
- 带「清空」出口，不把用户困在 0 条里

### 实测（jsdom 真输入）

```
初始                共 12,308 款
输入「赛博朋克」      6 款（508ms）
标题                搜索「赛博朋克」
清空                6 → 12,308
输入不存在的词        🔍 没有找到「zzzz不存在的游戏zzzz」
「侠」               63 款
「侠」+ 分类=动作冒险  30 款  ← 叠加，不是互相覆盖
```

## 4. 检查途中发现的第 4 件事：一屏两个数字对不上（本轮只加说明，不改口径）

截图核验时看到的：分类行写「库内 **19,766** 款」，列表写「共 **12,308** 款」。

两个数都没算错，但**一屏之内两个数互相矛盾**，用户只能理解成「有一个坏了」：

| 位置 | 数字 | 口径 |
|---|---|---|
| 分类行 `statlineHtml` ← `/api/library/stats` | 19,766 | 库内总量，**含**默认隐藏的冷门 |
| 列表 `#listCount` ← `/api/library/browse` | 12,308 | 剔除冷门后的**可见**口径 |

这是 v10.84 引入冷门隐藏时就带来的口径并存，不是本版引入。

**本轮只给「库内」那三个字加了 `title` 说明**，没有改数字：

```html
<span title="库内总量，含默认隐藏的冷门条目（列表的「共 N 款」是不含冷门的可见口径）">
```

为什么不顺手改掉：改数字要动 `/api/library/stats` 的返回口径（`total` 与 `bySource` **三个字段一起**），
而这三处被多条断言引用。改口径的风险大于收益，**先记进遗留（§6）**，等做后台 chip 双维那一版
一起处理 —— 那时本来就要把「可见 / 全量」两个口径显式拆开。

## 5. 检查途中发现的第 5 件事：防线自己报假红（PID 复用 ⇒ 测试撞旧目录）

全量跑第三次时红了 `test-v1071-extractor` 的 D3/D7（`reachedDepth=1`，应为 2），
**单跑两次都是 50/50 绿**。查下来不是解压代码坏，是**测试自己的工作目录撞了**。

### 机制

```js
const ROOT = path.join(__dirname, '..', '_test-out', 'v1071-verify-' + process.pid);
```

1. 目录名只有 **PID**；
2. **Windows 会复用 PID** —— 全量跑时 86 个 node 进程快速起落，撞上旧 PID 的概率远高于单跑；
3. 撞上之后，目录里已经是**上一轮解压好的文件**；
4. 解压器按设计带 `-aos`（跳过已存在文件，对应「破坏性操作要谨慎」的用户偏好）
   ⇒ 退出码 **0**、`produced=0` ⇒ `reachedDepth=1` ⇒ D3/D7 假红。

**退出码 0 让一切看起来都成功** —— 这是这条最难查的地方。

### 现场

```
_test-out/v1071-verify-*   110 个目录 / 1.1 GB
_test-out/v1071-api-*      125 个目录 / 1.9 GB
_test-out 合计             3.0 GB
```

### 为什么会写成这样

`_test-out` 本来**应该**每次跑完清理。但清理会撞「本 turn 累计删除 > 50」的安全删除守卫
（铁律 107 记录的那次 exit 1），于是改成「用 pid 保证唯一 + 不清理」。

**为了绕开一个问题而放弃清理，换来了另一个更隐蔽的问题。**
`pid` 从来不保证唯一 —— 它只是「同时存在的进程之间」唯一。

### 修法

```js
'v1071-verify-' + process.pid + '-' + crypto.randomBytes(3).toString('hex')
```

三个同族套件（`-verify` / `-api` / `-page`）一起改。仍然不做清理（会再撞守卫），
但**唯一性不再依赖清理**。顺手把 3.0 GB 残留清掉（`_test-out` → 26 MB）。

### 本版踩的两个测试坑

**① 计数型断言被自己的注释咬（铁律 201 同型）**

`test-cold-hide` 原本断言 `o.excludeCold =` 只出现一次。我在 server.js 里写了一句
「原本断言 `o.excludeCold =` 只出现一次」的**解释性注释**，计数当场从 1 变 3 判红。
修法不是改注释，是**给计数型断言统一加 `SRV_CODE`（剥块注释 + 整行行注释）**。

**② 拿「标题变了」当「数据回来了」**

`renderList` 的执行顺序是「先改标题 → 再 fetch → 最后写计数」。
`D1` 第一版等标题变化，于是在标题变的一瞬间读到了**上一条搜索留下的 0**
（「侠」真实 63 条被记成 0，后面的叠加实验全部错位）。
改成等「计数真的离开旧值」——离开的那一刻才是新结果落地的时刻。

**③ 全量跑时那套「数据类断言集体红」**

第四轮全量跑时 `test-emulator-page` 一次红了 **9 条**，特征是「所有异步数据都没回来」：

```
data-ready 3863ms（单跑 128ms，慢 30 倍）
指南技术栈 5 层已渲染      实际 0
品牌下拉已填充             实际 1 项（只有 placeholder）
Turnip 驱动看板已渲染       实际 0 个变体
机型匹配结果已渲染          实际 0 张（等待超时 12000ms）
点「💾 有云存档」… 卡片 0
```

不是功能坏（单跑 101/101），是**固定 `sleep(1200/1500/1600)` 在被压满的机器上先于数据到达**。
把 5 处改成「等目标节点出现」（上界 30s，超时照旧红并把等待耗时打进详情）后，
单跑实际等待 **125~260ms** —— 比原来死等 1.2~1.6s 更快，也更准。

这是铁律 221 的**第 5 例**（同一文件）。剩下约 10 处固定 sleep 仍登记为技术债。
