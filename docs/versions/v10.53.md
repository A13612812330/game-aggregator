# v10.53 —— 首页卡面补上「资源维度」+ 三个筛选改与卡面同源 + 下载弹窗补 GTrainers 腿

> **一句话结论**：首页卡片只有 `📱 可玩` / `🎮 实测` 两枚**手机端**徽标，而筛选行里**已经有**
> `🛠 有修改器` / `💾 有存档` 两个开关 —— 筛出来的卡片上**没有任何对应标记**（实测旧 `💾` 口径

**关键实现 1 —— 「同源」不是口号，是一条可断言的性质**：

```js
/* data/res-groups.js */
const libIds = { mod: new Set(), saves: new Set(), trainers: new Set() };
for (const c of Object.keys(gByCat)) {
  for (const x of gByCat[c]) if (x.key.startsWith('L:')) libIds[c].add(x.key.slice(2));
}
```

筛选（`libIdsFor`）与卡面 chip（`countsFor`）都从 **`byKeyCat.get(cat + '|L:' + id)`** 这一张表出，
所以「**筛出来的每一款，卡上都有对应 chip**」不是巧合，是可断言的不变量 —— 已写成
`test-v1053-home-res.js` 的 Phase B（三个筛选**逐档**验 `withChip === cards`）。

⚠️ **只收 `L:` 前缀键**：`N:`（按名归组、拿不到库内 id）塞进集合会造出**死 id**
（筛出来点不动）。

**关键实现 2 —— 弹窗补 GT 腿（本轮真正贵的那一处）**：

```js
/* 修改器分支：三路并行 */
const [community, gcm, gtr] = await Promise.all([
  dlUniFetchMods(st.ctx, k),
  k === 'modifier' ? dlUniFetchGcm(st.ctx) : Promise.resolve([]),
  k === 'modifier' ? dlUniFetchGt(st.ctx, 'trainers') : Promise.resolve([]),
]);
st.cnt[k] = community.count + gcm.length + gtr.length;

/* 存档分支：三路并行 */
const [files, loc, gts] = await Promise.all([
  dlUniFetchSaveFiles(st.ctx),
  dlUniFetchSaveLoc(st.ctx),
  dlUniFetchGt(st.ctx, 'saves'),
]);
st.cnt.save = files.count + gts.length;   // ← 仍然**不含位置条数**
```

三个不能省的细节：

- **GT 段排在「出口链接」之前**。出口是「去别处找」，内容是「已经找到了」——
  排反了会被读成「这一屏到此为止」。
- **机地空态在 `gtr.length` 时不写「去机地搜」**。否则同一屏里「没有收录」与下面列出的
  GT 条目**自相矛盾**（这一格是实测撞到的）。
- **下载通道放 `.bd` 第三行（`.dl-res-lk`），不塞行尾 `.go`**。GT 一条常有 2~4 个真通道，
  `.go` 是 `flex:none`，塞进去窄屏会把标题挤没。

## 二、根因与数据（全部实测，2026-10-10）

### 2.1 缺口量化：卡面与筛选各说各话

| 项 | 改前实测 | 说明 |
|---|---|---|
| 首页默认视图 40 张卡 | 只有 **3 张**带 chip | 绝大多数卡面看不出「这游戏有资源」 |
| 旧 `💾` 筛出的 5,119 款 | 卡面 chip 数 = **0** | 筛出来**看不见为什么**（旧口径筛的是「位置库」） |
| 筛选开关数 | **4** | 有 `有修改器` / `有云存档`，但卡面不标 |
| 卡上挂 `🛠` 的 GTrainers 款 | **1,300** | 旧 `tr` 口径（2,391）**筛不到**它们 |

### 2.2 新旧口径对照（这就是「同源」的实证）

| 分区 | 聚合层 `libIdsFor`（**新**） | xref 旧口径 | 差异根因 |
|---|---|---|---|
| `mod` | **264** | ——（无旧口径） | —— |
| `trainers` | **3,691** | `xref.trainerIds()` = **2,391** | 差 **1,300** 款 = **只有 GTrainers** 的那些（GT 修改器 5,510 条覆盖） |
| `saves` | **1,377** | `xref.saveIds()` = **6,274** | 旧的是 Ludusavi **位置**库（「放哪」），新的是**能下到的文件**（「下什么」）—— **差 4,897 款是口径不同，不是数据丢了** |

★ 反向验证一条：聚合层里 **`trainers` 的非 GT 款 = 2,391 = `xref.trainerIds()` 的集合大小**（逐一相等）
⇒ 证明新口径严格是旧口径的**超集**，不是把旧数据换掉了。

### 2.3 ★★ 弹窗空页签：GT-only 占比（本轮的核心缺口）

按「库内 id 能对应上」的组统计（`libIdsFor` 逐组看来源）：

| 分区 | 有资源的款数 | **只有 GTrainers** | 占比 |
|---|---|---|---|
| `🛠 有修改器` | 3,691 | **1,300** | **35.2%** |
| `💾 有存档` | 1,377 | **842** | **61.1%** |
| `🧩 有 MOD` | 264 | **0** | 0%（GT 不提供 MOD ⇒ `mod` 页签**不需要**补这条腿） |

⇒ 这 842 / 1,300 款游戏，改前点 chip 进去是**空页签**（页面不报错、只是什么都没有）。
`mod` 分区 0% 这个数也顺手定了一件设计：**`dlUniFetchGt` 只给 `modifier` 与 `save` 两个页签**，
`mod` 页签不挂（挂了就是一条永远空的段）。

## 四、踩到的坑

1. ★★ **负向断言要锚「不许加什么」，不能锚「不许加任何东西」**。`test-download.js` 里
   v10.46 写的那条 `!/st\.cnt\.save = files\.count \+ /` —— 当时意图是「不许把**位置条数**加进角标」，
   但写成了「不许加任何东西」。v10.53 把 `+ gts.length` 加成**设计要的**行为后，这条**当场假红**。
   ⇒ 改判据为 `!/st\.cnt\.save = [^;]*\bloc/`（钉住 loc）。**这是「负向断言写宽了会在设计变更时
   变成阻力」的现场**：它会让维护者误以为「改动错了」，而真正错的是断言的范围。
2. ★★ **反证脚本的注入点不要写死缩进**：首跑 `【4/7】` 直接**抛**
   （`反证注入点没匹配上：server.js`）—— 源码那两行是**两个**空格缩进，我写了四个。
   改 `\s*\n\s*` 后通过。★ 庆幸的是 `patch()` 里那条 `if (!re.test(s)) throw` 让「注入失败」
   **抛而不是静默** —— 否则反证会变成「一条都没红」然后被读成「护栏是假绿」。
   ⇒ 与铁律 38 同族：**没测到 ≠ 没坏**。
3. ★★ **常驻服务的代码改动，浏览器层看不到**（见第三节 A 支说明）。这条第一次遇到时
   差点把「浏览器套件没变红」写成「断言守不住」——**实际是靶子没换**。
   判据：被测端是**磁盘文件**（前端/静态）还是**常驻进程**（服务端）要分开看。
4. ★ **收尾汇总行的格式是约定**：我第一版写 `48 通过 / 0 失败`，`run-all` 的
   `\d+\s*\/\s*\d+` **匹配不上**（数字中间夹了「通过」）⇒ 成绩退化成从明细里猜，
   实测被上一行 `40/40`（那是个**明细串**）顶掉，整套被记成 40 条。
   改成 `' + pass + ' / ' + (pass + fail) + ' 通过'` 后正确计入 48。
   ⇒ `run-all` 现在会**显式警告**这类套件（v10.52 加的收口），但**新套件第一次写就要按约定来**。

## 五、★★ 本轮真正的架构性收获

### 5.1 「筛选」与「卡面」必须是同一张表算出来的

改前：筛选读 `xref.trainerIds()`（2,391 款），卡面 chip 读 `resGroups.countsFor()`（口径另一套）。
两者**各自都对**，但**互相对不上** ⇒ 用户看到的是「筛出来看不见为什么」+「卡上有标记却筛不到」。

⇒ 判据：**凡是「筛选项」与「列表上的标记」同时存在的地方，它们必须由同一个函数出。**
本项目落了三条同源断言（`libIdsFor` / `countsFor` 同出 `byKeyCat`；接口 `total` = 集合大小；
卡面 `withChip === cards`），并已反证（换回 `xref` ⇒ 两道闸同时红）。

### 5.2 聚合层建好之后，**每一个消费者**都要单独接线

v10.47 建 `data/res-groups.js`，v10.52 接了搜索，v10.53 接了首页卡面 / 筛选 / **弹窗**。
**同一个聚合层，五次被发现「某个消费者没接」**。这不是巧合，是结构性的：
新层建好时只接了当时想到的那个消费者，其余消费者**沿用旧口径继续工作，且不报错**。

⇒ 建议的固定动作：新建聚合层后，**列出全部消费面清单**（本项目已有 6 个：卡面 chip / 搜索行 /
首页筛选 / 资源页 / 详情抽屉 / 下载弹窗），逐个核对。v10.53 的弹窗就是清单上最后一个。

### 5.3 「空页签」是比「空列表」更隐蔽的失效形态

- 空列表：至少能看到「没有」这句文案，用户会去别处。
- 空页签：**卡上明明写着 3**，点进去一片空白，且**页面不报错**、防线也不报错。

⇒ 只要「入口上的数字」与「入口里的内容」来自不同代码路径，就必须有一条断言把两者焊死
（本版 = Phase E 的 `rows === counts`）。
