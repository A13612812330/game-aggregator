# v10.91 —— 后台鉴权从「人记令牌」改为「管理员账号（用户名 + 密码）」

> 用户原话：「为什么要令牌，不如直接给我一个管理员账号，设置成 liyou，密码为 Ly123321」

## 一、先回答「为什么要令牌」，以及为什么现在改

令牌（v10.87 引入）解决的是**机器鉴权**问题：线上部署在反代后面，`remoteAddress` 恒为代理地址，
只靠「回环放行」等于公网裸奔。当时需要一个不依赖 Cookie、能塞进请求头的凭据。

但令牌被当成**人的登录方式来用**，就会露出三个天然缺陷，而且都不是「再优化一下」能解决的：

| 缺陷 | 表现 | 为什么治不好 |
|---|---|---|
| 不可记忆 | 48 位 hex，只能靠粘贴 | 它的设计目标就是「不可猜」，天然不可记 |
| 不可核对 | 填错和填对长得一样 | 只能靠服务端判，用户无法自查 |
| 保管成本 | 存在哪、发给谁、怎么轮换 | 每轮换一次就要通知所有使用者 |

⇒ 本轮把**人**的通道换成账号密码，**令牌通道保留给程序**（抓取脚本、`verify-online`、
各测试套件的无头鉴权全靠它，砍掉会连带弄坏一批防线）。这不是没删干净，是有意的双轨：
**人用账号，程序用令牌。**

## 二、设计：口令只在服务端比对

最关键的一条：**密码绝不能写进前端**。

如果做成 `if (u === 'liyou' && p === 'Ly123321')` 这种前端硬编码对比，任何人
`View Source` 就能拿到密码 —— 那比令牌更糟（令牌至少不在页面里）。所以：

```
浏览器                          服务端
  │  POST /api/admin/login {user, pass}
  │ ────────────────────────────────►
  │                          scrypt(pass, salt) === 落盘 hash ?
  │                          ✔ 签发随机 sid（32 字节）
  │ ◄────────────────────────────────
  │  localStorage: gh_sid=<随机串>      SESSIONS: Map<sid, {user, exp}>
  │  之后每个请求 X-Admin-Session: <sid>
```

- 浏览器手里只有**随机串**，它本身不含任何信息量；口令从不落浏览器存储。
- 落盘只存 `scrypt(pass, salt)` + 随机 salt（`data/admin-account.json`），明文不落盘、不入库。
- 会话存**进程内存**：重启 / 发布后全部失效 —— 宁可让用户重登一次，也不把会话写盘
  （写盘就等于再造一份凭据文件）。
- Cookie 同时下发（`HttpOnly; SameSite=Lax`，只有 https 才加 `Secure`），
  自定义头被反代剥掉时还有一条路；`?sid=` 只在 403 之后才降级使用，正常路径不把会话写进 URL。

### 三条通道（服务端任一成立即放行）

| 顺序 | 通道 | 谁在用 | 判定 |
|---|---|---|---|
| 1 | 回环 | 本机 8123/8124 调试 | socket 回环 **且** Host 本地 **且** 无任何转发头（v10.87.1 的三条件 AND） |
| 2 | 会话 | 人（浏览器） | `gh_sid` Cookie / `X-Admin-Session` 头 / `?sid=` |
| 3 | 令牌 | 脚本、无头核验、测试 | `X-Admin-Token` / `?token=` / `body.token` |

## 四、安全上的四个取舍（都实测过）

### 1. ★ 限流必须按真实客户端 IP，不能按 socket

第一版 `clientIp()` 直接取 `req.socket.remoteAddress`。线上所有请求的对端都是**同一个反代地址**
⇒ 一个人爆破 8 次，**所有人**都被锁在外面 10 分钟。

本机实测抓到的正是这个形态：脚本连错 8 次之后，浏览器用**正确密码**登录也吃 `429`。
修法：`X-Forwarded-For` 第一段优先。

### 2. XFF 可伪造 ⇒ 加一道全站兜底

按 IP 限流本身可以被伪造 XFF 绕过。补一道「全站 10 分钟内失败 500 次」的闸门：
正常使用永远碰不到，只有真的在被爆破时才触发。代价是被爆破期间登录也会被挡 10 分钟 ——
这是**可用性 vs 抗爆破**的有意取舍，阈值取高就是为了让它几乎不触发。

### 3. 错误信息不区分「用户名错」与「密码错」

统一回「用户名或密码不正确」，避免被用来枚举账号（`D5` 断言守着）。

### 4. 改密码不强制下线

会话在内存里按 `exp` 过期，改密码不影响已签发的会话。
这是有意的（不该把正在用的人踢掉），但也意味着**改密码 ≠ 强制下线** ——
需要立刻踢人时重启进程或调 `/api/admin/logout`。

## 五、顺带修掉一个显示 bug：「数据源健康」印出 `NaN%`

实拍登录后的仪表盘时看到三行是 `NaN% · —,6,632` / `NaN% · —,9,346`。

根因：那张表统一读 `.matched / .total`，但**六个源 `stats()` 的字段名各不相同**：

| 源 | 真实字段 | 原来读的 | 结果 |
|---|---|---|---|
| 机地帖 MOD | `matched / total` | 同 | ✅ 96% |
| 修改器 | `matched / total` | 同 | ✅ 77% |
| 存档（Ludusavi） | `inPcLib / total` | `.matched` | ❌ NaN |
| 云存档 | `withCloud / total` | 没这一行 | — |
| GTrainers | `preMatched / listTotal` | `.matched / .total` | ❌ NaN |
| FitGirl | `matchedGames / lib.total` | 同 | ✅ 29% |
| Thunderstore | `matched / communities`（**没有 total**） | `.total` | ❌ 0% · 254/— |

修法两条：**逐源写真实字段名** + **取不到就显示「—」**（而不是印 NaN）。
后者比前者重要：下次某个源再改字段，这一行会**明显变灰**，而不是安静地印一串 NaN。
实拍复验：`96% · 8,594/8,943` / `77%` / `96% · 6,334/6,632` / `80%` …，探针 E8 守「渲染结果里不许有 NaN / undefined」。

## 六、踩坑

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 浏览器实拍显示「令牌」而不是「未登录」 | 上一轮令牌探针在同一个浏览器 profile 里留了 `gh_admin_token` | 探针先清 `localStorage` 再 reload；不是产品 bug |
| 2 | 正确密码登录吃 `429` | 见四·1（socket 地址当作客户端 IP） | 改 `X-Forwarded-For` 优先 |
| 3 | `F1 刷新后 0 行` | 断言查的是「页面管理」表格，而刷新后落在仪表盘 | 断言前先 `go('pages')`；产品行为正确 |
| 4 | `G1 弹窗分组=0` | 判据用了**不存在的 class** `.pfgrp`（真实是 `#pfCrawl` / `#pfData1`）⇒ 恒为 0，等于没判 | 改成真实 id + 判 `display` 差异 |
| 5 | 首屏状态一会绿一会红 | `paintAcct()` 与并发的 verify 抢跑 | 启动改成「先 verify 再渲染」 |
| 6 | 控制台满屏 403 日志 | 未登录时的 403 是**预期结果**（横幅就是靠它触发的） | 探针按阶段（boot/in/out）分别统计 4xx，只对 `in` 阶段零容忍 |

## 八、边界与待办

- ⬜ **线上 `data/` 会在每次发布时被本地载荷覆盖** ⇒ 线上改过的账号会在下次发布时回到本地那份。
  长期修改请改本地再发布（与备注/豁免/资料覆盖同一规则）。
- ⬜ 会话是内存态：**每次发布后需要重新登录一次**。
- ⬜ 密码强度：当前口令 8 位字母+数字。限流能挡住在线爆破，但挡不住离线破解 ——
  如果哪天这个哈希文件外泄，建议改成 12 位以上随机串（`set-admin-account.js` 一条命令）。
- ⬜ 未做二次验证 / 会话列表 / 主动踢人（当前只能重启进程）。
- ⬜ `data/admin-account.json` 已进 `.gitignore`；**发布载荷会自动带上它**
  （载荷规则是「复制 data/ 下除 `_*-raw` 之外的全部」），所以线上能登录。
