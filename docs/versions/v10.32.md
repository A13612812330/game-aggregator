## 一、① 定位条：修改器 / 云存档**合并成一项**

### 为什么 v10.29 保留两项的理由站不住

v10.29 把两块改成 `.d-pair` 两列同一行时，**特意**在定位条上保留了两项，理由是
「两块内容完全不同，只留一项会让『云存档』在条上彻底消失」。实测这个理由反了：

- 两块既然并排，它们的 `getBoundingClientRect().top` **只差几像素**；
  而 `railSpy()` 的高亮判据是「最后一个越过视口顶部 +90px 的分区」
  ⇒ 滚到这一行时**两项同时变蓝**，两个序号一起点亮；
- 点哪一项都跳到**同一行**（`scrollTo` 的目标差几像素，视觉上完全一样）。

⇒ 定位条是按**屏幕位置**切的，不是按内容切的。两块共享一行 = 只有一个位置。
（实测：改造前 **9 项**，改造后 **8 项**，合并项名为「修改器/云存档」。）

### 改法

```js
/* v10.31 及以前 */
{ k: 'tr', nm: '修改器', sel: ['#trBlock'] },
{ k: 'sv', nm: '云存档', sel: ['#svBlock'] },

/* v10.32 */
{ k: 'trsv', nm: '修改器/云存档', sel: ['#trSvSlot'] },   // ← 指向两块的共同容器
```

`#trSvSlot` 就是那个 `.d-pair`（`<div class="d-pair" id="trSvSlot"><div id="trBlock"></div><div id="svBlock"></div></div>`）。
`railTarget()` 本来就会跳过「存在但没内容」的节点：两块都没数据时 `.d-pair` 高度为 0，
这一项**自然不出现**，不需要额外写逻辑。

## 二、② 定位跳转「顶部被遮挡部分」—— 遮挡物是**常驻小标题条**

### 根因：一个不占布局高度、却恒覆盖 62px 的 sticky 元素

```css
.d-mini{position:sticky; top:0; z-index:7; height:62px;
        margin-bottom:-62px;      /* ← 关键：不占布局高度 */
        ...}
```

它显形后**恒定覆盖抽屉内容最上方 62px**，但因为 `margin-bottom:-62px`，
它**不影响任何元素的 `rect`** —— 所以「只看 rect 数值」根本看不出被盖住了。

而旧的跳转落点只手留 14px 余量：

```js
dr.scrollTo({ top: Math.max(0, dr.scrollTop + dy - 14), behavior: 'smooth' });
//                                        ↑ 62 - 14 ≈ 48px 落进小条底下
```

### ★ 反证实测复现了它：`gap = -47`

把余量写回旧值（`raw - cover - gap` → `raw - 14`）后跑实拍：

```
· 评分参数  gap= -47  小条=62px  落点=（空）  ❌被小条挡住
```

`-47` ≈ `62 − 14` —— 与推算完全吻合，这就是用户说的「遮挡部分」。

### 改法

```js
const mini = $('#dMini'), hero = $('#dHero');
const miniH = mini ? mini.offsetHeight : 0;     // 62：小条自身高度
const heroH = hero ? hero.offsetHeight : 0;     // 250：小条显形阈值（与 dHeroSpy 同源）
const dy = el.getBoundingClientRect().top - dr.getBoundingClientRect().top;
const raw = dr.scrollTop + dy;                  // 目标落点（不含任何余量）
const cover = raw >= heroH ? miniH : 0;         // 跳过去时小条会不会显形
const gap = cover ? 10 : 14;                    // 显形才减，且只留 10px
dr.scrollTo({ top: Math.max(0, raw - cover - gap), behavior: 'smooth' });
```

⚠️ **不能无条件减 62**：小条只在 `scrollTop >= 大图高` 时才显形（见 `dHeroSpy`），
而「评分参数」这类紧跟大图的分区跳过去后可能还没过阈值 —— 那时多减 62 会把目标顶到半空。
所以先算 `raw`，**再按它判**。

## 三·补、④ 修改器 / 云存档：底部提示文案统一为**三行**

### 先量，再改（用户口径「真实数据、不要形容词」）

探针 `tools/_probe-v1032-hint.js`（xd-692 史莱姆牧场，渲染后实测）：

| 项 | 修改器 | 云存档 | 判定 |
|---|---|---|---|
| 卡片高 | 330.4 | 330.4 | 已同高 ✅ |
| **提示文案渲染行数** | **4 行** | **3 行** | ❌ 差一整行 |
| **提示块高度** | **77.3px** | **59.9px** | ❌ 差 **17.3px** |
| 硬换行 `<br>` | 1 | **0**（靠自动折行） | ❌ 结构不一致 |
| 字号 / 行高 / 颜色 | 10.5px / 17.325px / `#9aa3b5` | 同 | 一致 ✅ |
| 提示底距卡底 | 11.0 | 11.0 | 一致 ✅ |

⇒ 根因：**修改器那段文案实际排到 4 行**，比云存档多一行；而且只有它用 `<br>`，
云存档靠自动折行（宽度一变行数就变）。两块底部因此**高度不等、上边缘错开**。

### 改法：两段统一为「用法 → 注意 → 来源」三行骨架

```html
<!-- 修改器 -->
文件放到<b>游戏安装根目录</b>（与主程序 .exe 同级）。<br>
启动前先运行 Cheat Engine，再加载 CE 表格。<br>
数据来自 Game Cheats Manager，<a href="…">打开 GCM 下载页 ↗</a>

<!-- 云存档位置 -->
路径中的 <code>&lt;用户名&gt;</code> / <code>&lt;平台账号ID&gt;</code> 是占位符。<br>
按你自己的账号替换；<b>存档前先退出游戏</b>，避免被覆盖。<br>
数据来自 Ludusavi 开源清单（MIT）。
```

**为什么是「显式 `<br>`」而不是「把文字删到刚好三行」**：靠自动折行时，
行数随**容器宽度**而变（抽屉宽 `min(clamp(680px,50vw,1040px),100vw)`）——
视口 1440px 时提示宽 306px、视口 761~1360px 时最窄 **286px**。
用 `<br>` 钉死行数，两块永远都是 3 × 17.325 = **51.975px** 文字高；
同时**每行都控制在 ~25 全角当量以内**（286px ÷ 10.5px ≈ 27.2），保证最窄那档也不折行。

**「不是说真预留」怎么落的**：没有加任何空白槽位（`.d-rows` / `--d-rows` 一行没动），
只改文案本身的排布；两卡同高仍由 `.d-pair{align-items:stretch}` + `margin-top:auto` 保证。

### 效果（8 档视口实测，`_probe-v1032-hint.js` 扫 W=600…1440）

| 视口 | 提示宽 | 行数（修改器/云存档） | 提示高 | 高差 |
|---|---|---|---|---|
| 1440 | 306px | 3 / 3 | 59.9 / 59.9 | **0** |
| 1360 · 1200 · 1000 · 800 · 761 | **286px** | 3 / 3 | 59.9 / 59.9 | **0** |
| 760 · 600（单列） | 690 / 530px | 3 / 3 | 59.9 / 59.9 | **0** |

改造前 → 改造后：提示高差 **17.3px → 0**；行数 **4/3 → 3/3**；两块提示上下边缘**同时对齐**。

### ★ ③ 是这一版唯一**页面特征串抓不到**的改动

③ 改的是 `data/pcreq.js`（服务端），首页 HTML 里**没有那些函数名** ⇒
`verify-online.js` 的 `includes` 式页面判据对它**完全无效**。
⇒ 本次把验收扩到**接口层**，直打线上两个端点：

```js
/api/pcreq?t=生化危机9：安魂曲/Resident_Evil_Requiem
  → hit=true · appid=3764200 · name=Resident Evil Requiem · 最低配置=有 · 推荐配置=有
/api/pcreq/stats
  → cached 712 / withReq 707 / miss 4 / ★ searchKeys 1
```

`searchKeys` 是 v10.32 新加的字段（把「按名称搜出来的 `q:` 缓存键」与 appid 键**分开计数**，
否则「收录多少款」会虚高）⇒ **字段在 = 新版 pcreq.js 在**，是一条与页面无关的独立证据。
