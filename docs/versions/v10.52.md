### 2.2 ★ 孪生条目陷阱（本轮实测踩到，已修）

端游库里**同一款游戏常有 jidi / xd 两条**（双料 **13,448**），而资源条目只挂在**其中一条**上：

| 条目 | `resGroups.countsFor()` |
|---|---|
| `xd-191` | `{mod: 717, saves: 104, trainers: 22}` |
| `jidi-3277800` | `{mod: 0, saves: 0, trainers: 0}` |

而搜索结果**第一行**（也是主行）恰恰是**机地那条**。首版 `withRes` 只查 `countsFor(g.id)`
⇒ 主行显示「没有资源」，而它下面那条反而挂着 717 —— **读起来像 bug**。

修法：`resFor()` 加孪生兜底，复用 `data/twin.js`（双源对齐的**唯一真源**，铁律 17）：

```js
function resFor(g) {
  let r; try { r = resGroups.countsFor(g.id); } catch (e) { return null; }
  if (r.mod || r.saves || r.trainers) return { counts: r, id: g.id };   // 自己那条有 ⇒ 不白跑
  try {
    const tw = twin.twinOf({ id: g.id, title: g.title, src: g.source });
    const t = tw && tw.url ? parseDetailUrl(tw.url) : null;
    if (!t) return null;
    const alt = (t.source === 'jidi' ? 'jidi-' : 'xd-') + t.id;
    if (alt === g.id) return null;                    // 兜回自己 ⇒ 没有另一条
    const r2 = resGroups.countsFor(alt);
    return (r2.mod || r2.saves || r2.trainers) ? { counts: r2, id: alt } : null;
  } catch (e) { return null; }
}
```

两条路径都是**精确键**：机地条目走 `jidiIdIndex()`（记忆化 Map、O(1)），XD 条目走 `jidiUrl + tidOf()`。
这里不需要「尽力而为」，只需要「准」。
⚠️ **只在「自己那条为 0」时才去找孪生** —— 绝大多数条目本来就没资源，每次都查等于给搜索加一趟白跑。

## 四、踩到的坑

1. ★★ **断言钉错了「实现位置」而不是「意图」**：结构套件新加的「全 0 不挂字段」首版判据是
   `if (r.mod || …) o.res = r;` —— 但那个判断后来**移进了 `resFor()`**，套件当场 239/240 红。
   按项目规矩：**先确认意图未变（仍要「全 0 不许挂字段」）再改判据**，改成同时钉住三处
   （`return { counts: r, id: g.id }` / `return … ? { counts: r2, id: alt } : null` /
   `if (h) { o.res = h.counts; o.resId = h.id; }`）。→ 241/241。
   **教训**：断言要钉「行为不变量」，钉「某个函数体的某一行」会在重构时集体假红。
2. ★★ **反证脚本自己写错了判据**（首跑 14/15）：分支 B 里匹配报错文案的正则**抄的是浏览器套件那句**

   改判据 → 15/15。**这正是「反证脚本自己要能被反证」的现场**（与 v10.51 同类，已第二次）。
3. ★ **`curl` 在沙箱里走代理**：`curl http://127.0.0.1:8123` 报
   `upstream connect failed: 目标计算机积极拒绝` —— 一度误判成「服务挂了」。

## 五、★★ 本轮真正的架构性收获

### 5.1 「聚合层建好了，消费端没接线」是一类独立缺陷

`data/res-groups.js` 在 **v10.47** 就建好了，注释里写得分明：

> `countsFor(libId)` —— 详情页挂「本游戏有 N 条 MOD / 存档 / 修改器」

但这个函数**只有详情页在调**，搜索链路一次都没调 ⇒ 数字在服务端躺着，用户看不见。
这跟「数据源没有」症状**一模一样**（界面上就是没有），但根因完全不同：
**改采集是白干，改接线一行就够**。

⇒ 已出现的 4 次全部同族（v10.48 / v10.50 / v10.51 / v10.52）。第 5 条铁律级的判据：

> 界面上缺一个数，**先问「这个数在服务端有没有被算出来过」**，
> 再问「数据源有没有」。前者成立时改动量是后者的百分之一。

### 5.2 ★ 只要数字是从**别的记录**算出来的，就必须连「它是谁的数字」一起下发

这是本轮最贵的一条。孪生库（jidi / xd 双料 13,448）让「条目 id」与「计数归属 id」**解耦**：

| | 显示条目 | 计数归属 |
|---|---|---|
| 赛博朋克2077 | `jidi-3277800` | **`xd-191`** |
| 后果 | 主行看着像「没资源」 | 拿显示 id 查库 ⇒ 查空 |

首版把 `resId` 省了，靠 `/api/mods/match` 的**名称模糊兜底**其实也能撞对 ——
但那意味着**同一份数据在两条路径上得到不同结果**，且差异不可预测。
补 `resId` 只多 20 字节回包，却把「运气」换成「设计」。

⇒ **推广**：任何「A 记录的详情里显示 B 记录算出来的数」的场景，
回包必须带 `{value, ownerId}` 两个字段，前端不许用 `A.id` 代替 `ownerId`。

### 5.3 副产品：建了聚合 ≠ 建了入口

同一次核实时发现 **`gt/match` 与 `jiditopics` 在四页里引用数都是 0**：

| 接口 | 数据在手 | 前端引用 |
|---|---|---|
| `gt/match` | 9,346 条（真直链 98.8%） | **0** |
| `jiditopics` | 17,220 条话题（364 款带 MOD 计数，合计 7,804） | **0** |

⇒ 这两条正是用户要的第 4 条线（**每模块数据关联**）的靶子，排进 v10.54。
