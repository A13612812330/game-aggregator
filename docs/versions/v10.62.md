# v10.62 —— 一款一行 + 联想面板带回「MOD / 修改器 / 存档」

> 日期：2026-10-12 ｜ 承接 [v10.61](v10.61.md)（两级归并键：名称键 ∪ Steam AppID）
> 前端主源改动 ⇒ **三张派生页已重建**（铁律 1）

## ① 起因（用户两条原话，紧接 v10.61 交付之后）

> 「每个游戏仅需要提供一个即可，其次我要的mod/修改器/存档也没提供给我」

两条都针对**同一个界面**：搜索弹窗的**联想面板**（打字 180ms 出结果的那个）。

| # | 用户看到 | 实际机制 |
|---|---|---|
| ① | v10.61 已把同款并成一行，但那一行下面还挂着 `↳ 另 1 个条目 [XDGAME 原版 ★9.1 ↗]` | `.sm-alt` 那排 chip 是 v10.25 设计的「同款聚拢后其余条目降级为 chip」 |
| ② | 面板里**一个** MOD / 修改器 / 存档都没有 | 联想接口 `/api/library` 只走 `withBh`，**从不挂 `res`**；而同一个 `smRow()` 在搜索结果面板里是有 chip 的 |

②的分量：同一行 UI、两个入口两个样。搜索结果里搜「赛博朋克2077」能看到 `🧩 717 MOD`，
联想里输入同一个词却什么都没有 —— 用户当然认为「你没给我」。

## ② 改了什么

### A. 前端：一款一行

- `smRows()` 不再拼 `smAltHtml(g)` ⇒ **每组只渲染主行**
- `smAltHtml()` 与 `smVariant()`（它唯一的调用方）**一起删除** —— 不留「看起来在维护、
  实际永不执行」的死代码
- `.sm-alt` / `.sm-alt-h` / `.sm-alt-b` **三族 CSS** 与响应式 `.sm-alt{padding-left:87px}` 一并移除
- `bindSmRows()` 里 `.sm-alt-b` 的点击绑定删除
- **归并键 `nkey` 与 `smGroup()` 一个字没动** —— 本次只改「组内其余条目要不要露脸」

### B. 服务端：联想接口改走 `withRes`

```
items: withNKeys(r.items.map(withBh))   →   items: withNKeys(r.items.map(withRes))
```

`withRes` 内部已经调 `withBh`，所以是**超集**：手机侧字段（`bh` / `pc`）照常带，
另加 `res` / `resId`。

### C. 前端：主行没有资源计数时**向同组借**

`res` 是**按条目**挂的。同组只渲染主行之后，万一主行恰好是没资源的那条，整组一个 chip 都出不来
—— 用户看到的仍然是「没有 MOD/修改器/存档」，等于没修。

⇒ `smGroup()` 归并后加一道：主行无 `res` 时，从同组找一条有 `res` 的借过来
（连同它的 `resId`；挂在**副本**上，**不改主行身份** —— url / title / 封面仍是首条那条）。

服务端 `resFor()` 已有一道**孪生兜底**（主行自身为 0 时去找孪生那条），实测
`jidi-3294040`(机地) 因此拿到了 `{mod:13,saves:9,trainers:4}`。前端这道是**第二道**：
两条不是孪生、只靠 AppID 并起来时，孪生兜底不会触发，只有组内互借能救。

## ③ 顺手修掉的一个真 bug：`withRes` 原地污染 gamesDb

排查②时撞见的现象：**同一个进程里，`/api/library` 带不带 `res` 是「随机」的。**

```
第一次：/api/library?q=三国无双      → jidi-3294040  res = null
复  测：/api/library?q=赛博朋克2077  → jidi-3277800  res = {mod:717, saves:104, trainers:22}
```

一度怀疑自己改错了代码。追下来是**顺序依赖**：

- `bannerhub.attach(g)` / `phonecfg.attach(g)` 都有 `if (!h) return g;` —— **两库都没命中时直传原引用**
- 原 `withRes` 是 `const o = withBh(g); … o.res = h.counts;` ⇒ 当 `o === g` 时就是**原地写**
  gamesDb 内存里的那条记录

⇒ 只要此前有人请求过 `/api/search/all`（走 `withRes`），那批条目就被**永久污染**：
在**整个进程生命周期**里都带着**当时那一刻**的计数（库更新后也不变，脏读），
并且漏进 `/api/library`、`/api/library/browse`、`/api/library/recent`、首页卡片。

修法：

```js
const b = withBh(g);
const o = (b === g) ? Object.assign({}, g) : b;   // 一律落在副本上；已是副本就不重复拷
```

★ 这也解释了为什么修污染与改 `withRes` **必须同时上线**：修之前联想面板能出现 chip
纯靠「先被 `/api/search/all` 污染过」，是运气；单独改任一处都会露馅。

## ⑤ 踩过的坑

1. **★ 断言被注释骗到**：`test-v1062.js` 里那条「响应式 `.sm-alt{padding-left:87px}` 也没了」，
   首跑**红** —— 因为我在 CSS 的说明注释里**原样引用**了这串字。改用锚行首的正则
   （`/^[ \t]*\.sm-alt\{…/m`），并补一条元断言专门守这个坑。
   （同一份文件里 F 段的元断言本来就在防「注释里的字样骗过正则」，结果自己先栽了一次。）
2. **★ 断言被别处的同名代码骗到**：A1 最初用全文件正则判 `items: withNKeys(r.items.map(withRes))`，
   但 `/api/search/all` 的端游桶里**有一模一样的串**（v10.52 就在那儿了）
   ⇒ 反证 A 打坏 `/api/library` 后断言**照样绿**。改成只取 `/api/library` 路由那一段（`LIB_SECT`）。
   **反证的价值就在这**：不写反证，这条假绿会一直藏着。
3. ★★ **`test-v1060.js` 的 C2 被本轮的改动打红（真红，`run-all` 首次跑出来的那 1 条）**：
   它钉着「`/api/library` 的 items 内层必须是 `withBh`」，本轮换成 `withRes` ⇒ 字面串失配。
   **同一个位置第 4 次因「钉调用形状」欠账**（v10.54 加 `fit` → v10.60 套 `withNKey` →
   v10.61 套 `withNKeys` → v10.62 换 `withRes`）。
   ★ 更值得记的是**它的邻居**：`/api/search/all` 那条用的是**全文件**正则，而两处的串长得几乎一样
   ⇒ 一旦有人把联想打回 `withBh`，邻居会**替它变绿**（`_counterproof-v1062.js` 坏法 A 实测证实）。
   ⇒ 两条都收窄作用域；前一条改判**意图**（「items 过了 `withNKeys`」），不再钉内层函数名。
4. **`&` 把整条 `cd && …` 链放进后台** ⇒ 父 shell 的 cwd 没变，后续相对路径全找不到文件。
   改用 `;` 分隔（`cmd1; cmd2 &` 里 `&` 只作用于 `cmd2`）。
5. **`node … & ` 起的服务随 shell 退出被回收** ⇒ 「起服务」与「跑探针」必须写在**同一条命令**里
   （v10.61 已记过，本次复用）。
