# v10.41 —— 「机型清单恒 6 台」定论：线上抓取失败仍回写缓存，把好数据打回空

> 起因：续做 v10.40 的收尾（推送到 GitHub）时，按铁律 14 复测线上，发现
> `tools/verify-online.js` 从 v10.40 记的 **31/31** 掉回 **25/31**，6 条红全部指向
> 同一件事：样本游戏「终极漫画英雄vs卡普空3」的机型清单**恒为 6 台**。
> 这正是 `PITFALLS.md` §十五.2 里写着「**成因未定论**」的那一条。

## 一、改了什么

|---|---|---|
| 1 | **`data/bhparams.js`：本轮抓取全部失败时不再落盘** | 修根因 —— 不再用「0 条」覆盖已有好数据，也不再刷新 ts |
| 2 | **`/api/bh/params` 返回体新增 `allFailed`** | 让调用方能区分「这款真没有配置」与「这次没抓到」 |

| 4 | **登记进 `tools/run-all.js` 的 `SUITES`** | 否则新套件永远不会被防线覆盖 |
| 5 | **`PITFALLS.md` §十五.2 从「成因未定论」改成定论** | 附完整证据链与修法 |
| 6 | **更正 `docs/versions/v10.40.md` §七 的错误归因** | 原文断言那 6 条红「根因是线上运行时数据陈旧、已自愈」—— **是错的** |

## 二、根因链（一条链，四步）

```
线上沙箱访问 raw.githubusercontent.com 全部失败
  → data/bhparams.js 的 params() 抓到 0 条
  → 旧代码无条件执行 c[key] = { ts: Date.now(), total: 24, items: [] } 并 flush() 写盘
  → ① 已有的好数据被「0 条」覆盖
     ② 写入的新 ts 让 7 天 TTL 重新计时 ⇒ 一周内不再重试
  → cachedDevices() 返回空 ⇒ /api/mobilehub/match 的 devices 只剩上游聚合摘要的 6 台
```

关键在那两行**无条件写盘**：

```js
c[key] = { ts: Date.now(), total: list.length, items };   // items 可能是 []
dirty = true; flush();
```

`params()` 里 `mapLimit` 把每条抓取异常吞成 `null`、再 `filter(Boolean)`，
所以**「24 份全部失败」和「24 份全部成功」在下一行走的是同一条路** ——
一次网络抖动因此被固化成持久状态，还会因为 ts 刷新而**放大成一周**。

## 三、实测对照数据（三个实例打同一个接口）

判「是代码/数据问题，还是出网问题」用**三实例对照**：本地服务、载荷实例、线上。

| 实例 | `?k=ULTIMATE_MARVEL_VS__CAPCOM_3` | `/api/mobilehub/match` 机型数 |
|---|---|---|
| 本地 `127.0.0.1:8123` | `total=24` · `items=12` | **9 台** |
| 载荷 `127.0.0.1:8124`（`_deploy-gamehub`） | `total=24` · `items=12` | **9 台** |
| 线上 `gamehub-agg-v4` | `total=24` · **`items=0`** | **6 台** |

**同样的 key、同样的 24 份配置 URL、同样的代码** —— 只有出网能力不同。
⇒ 排除「载荷陈旧」「部署漏文件」「断言写错」，锁定**线上抓取失败**。

反证「不是版本问题」的旁证（线上与本地**完全一致**的接口）：

| 接口 | 线上 / 本地 |
|---|---|
| `/api/mobilehub/stats` | `builtAt=1790559424115` · `total=3252` · `matched=1657` **一致** |
| `/api/spec/dict` | `dict=v10.34` · `total=17268` · `archRule` 同 **一致** |
| `/api/device/market-stats` | `codes=8261` · `builtAt=1789613766094` **一致** |
| `/api/device/fill-stats` | `total=16` · `withChip=14` **一致** |

而 `/api/pcreq/stats` 这类**两边各自运行期写入**的缓存本来就不同（线上 `cached=17329` > 本地 `16371`）
⇒ 「线上与本地不一致」**不等于**「线上是旧版」，要按**取数来源**分开判。

本地缓存健康度实测：`data/bhparams.json` **16 个键 / 0 个**处于「`total>0` 但 `items=0`」的被打空状态。

## 四、修法（`data/bhparams.js`）

```js
if (!items.length && list.length > 0) {          // ★ 本轮全部失败：不落盘
  const prev = c[key];
  const kept = (prev && Array.isArray(prev.items)) ? prev.items : [];
  return { ok: true, key, picked: key, candidates: sizes,
    items: kept.slice(0, n), total: prev && prev.total != null ? prev.total : list.length,
    cached: kept.length > 0, allFailed: true, fetchedAt: prev && prev.ts };
}
c[key] = { ts: Date.now(), total: list.length, items };   // 只有抓到了才写
dirty = true; flush();
```

- **不写盘、不动 ts** ⇒ 下次调用仍会重新联网，网络恢复即**自愈**，不再锁死 7 天。
- `list.length === 0`（该 key 确实没有配置）走**上面**的分支，行为不变。
- 正常路径不受影响（由断言 【2】 单独守）。
