## ② ★★ 双源规模悬殊（100 vs 12）⇒ 直接用原始名次做 RRF 会让机地**塌陷式占位**

这是本版**技术含量最高的一节**，也是我第一版直接翻车的地方。

**实测事实**：机地 `hotRanks()` 有 `slice(0, 12)`，源站本身就只给 12 条；
XD 每档给 100 条。两源规模比 **≈ 8.3 : 1**。

第一版融合用最朴素的 `w/(K+rank)`（RRF）：

| 结果 | 数字 |
|---|---|
| 机地条目挤进前 11 | **7 / 11** ★ 病态 |
| 原因 | 机地 rank 1–12 vs XD rank 1–100 ⇒ 同一个 `1/(60+rank)` 下，机地 12 名的权重 ≈ XD 12 名的权重，而「12 名」对机地是**垫底**、对 XD 是**前 12%** |

**修法**：做**名次相对位置对齐**，而不是直接用原始名次：

```js
const N_REF = 100;
const scaleRank = (rank, n) => 1 + ((rank - 1) / (n - 1)) * (N_REF - 1);
```

即：把「12 条里的第 12 名」映射成「100 条里的第 100 名」。复跑后机地 ≈ **5 / 11**（健康区间）。

### ★★★ 反证 ① 照出一个更细的问题：**「结果形态」不能替代「算法语义」**

反证 ① 的做法是「把 `scaleRank` 打坏」，预期是「机地条目重新挤满」。
**但第一次打坏后机地仍然只有 5 / 11** —— 反证**不成立**（照不出红）。

根因不是判据写歪，而是**打歪了点**：当时我打的坏点是 **A15**，
而 A15 守的是 **tie-break 规则**「XD 名次优先」。真实链路里：

```
排序 → 分数相同 → tie-break（XD 优先）⇒ 机地即使分数高也会被交错开
```

⇒ A15 对 `scaleRank` 的失效**免疫**。真正该打的是 **A2**（榜尾对齐语义）。
把 need 改成 A2 后，反证立刻红。

**结论（已写进铁律）**：反证不充分有两种病因 ——
① **锚点选歪**（守 A 的断言去测 B 的改动）；② **锚点太宽**（子串匹配吃掉别的实现）。
两者症状一样（「打坏了还是绿的」），但修法完全不同：
前者要**回到被测语义**重选锚点，后者要**收窄作用域**。

## ③ ★★ 「压缩游戏图片」的真实根因：**三种源图的原始尺寸，全都不等于展示位比例**

用户说「放大适配游戏大图而不是压缩游戏图片」。我先量了三类封面的**真实尺寸**：

| 来源 | 原始尺寸 | 比例 | 大图变体 |
|---|---|---|---|
| Steam `store_item_assets/steam/apps/<id>/header.jpg` | **460 × 215** | **2.14 : 1** | — |
| XD `uploads/allimg/*-L.jpg` | **128 × 128** | 1.00 | 无 |
| 机地 `img2.52jidi.com/topic/cover/…/sz/src` | **140 × 140** | 1.00 | **无** |

★★ 机地的「大图变体」是**实测排除**的，不是推测：
`/src`、`/big/src`、`/lg/src`、`/xl/src`、`/ori/src` —— **全部 404**。

而 v10.74 的展示位是 16:9（1.78），且卡片是 4 列 ≈ 244×152 的方框：

| 症状 | 机制 |
|---|---|
| 「压缩/变形」 | 方图（1.00）塞进 2.14:1 的框 ⇒ `object-fit:cover` **上下各裁掉近一半**；反向若用 `contain` 则留白 + 图变小 |
| 「图太小」 | 140×140 的方图被**放大 3 倍**铺进 458×215 —— 分辨率根本不够 |

**实测 11 条里 4 条封面不达标**：2 条方图 + 2 条 Steam 图 **404**
（`apps/5024270/header.jpg`、`apps/3998800/header.jpg`）。

### 修法（三层）

1. **`coverScore(u)` 给封面打分**（新增，单一真源）：
   `steam/apps/<id>/header` → **4**；`steam/apps/<id>/其他` → 3；
   `community_assets/images/apps/` → 2；其他（XD allimg / 机地方图）→ **1**；空 → 0。
2. **融合时封面优选 + 同名提优**：从「固定优先级 `rec.cover || xd.cover || jidi.cover`」
   改成「**候选池按 `coverScore` 排序取最高**」，并在外层 `<=1` 时用 `byZh` 找库内同名条目
   **严格更优**才替换（内层护栏 `>` 而不是 `>=`，避免等分互换引入抖动）。
3. **前端两级 `onerror` 回退**：`this.src = this.dataset.alt` → 再失败则隐藏。

**修后实测（hot 档）**：`coverBigN` **11 / 11**，浏览器实测**全部 460×215 且全部 load 成功**。

★ 但**不是四档都满**，如实列出（`meta.coverBigN` / `coverSubN` 直接暴露短板）：

| 档 | coverBigN | coverSubN | 说明 |
|---|---|---|---|
| `recent` | 10 / 11 | 0 | 1 条库内确实只有方图 |
| `hot` | **11 / 11** | 2 | 2 条靠同名提优救回来 |
| `month` | 9 / 11 | 0 | 2 条库内只有方图 |
| `year` | **11 / 11** | 0 | — |

### ★★ 「放大大图」还有第二个坑，而且**只有守源码才拦得住**

这条是**反证实测出来的**，不是看代码看出来的。

`.rk-car` 从 v10.74 的 `height:200px` 改成 `aspect-ratio:var(--cover-ar)`。
但**移动端断点里留有 v10.74 的 `.rk-car{height:132px}`**。
`aspect-ratio` 与确定的 `height` 并存时会发生什么？实测三组（390 视口）：

| `.rk-car` 写法 | 实测渲染尺寸 | 结论 |
|---|---|---|
| 只写 `aspect-ratio` | **350 × 164** | 撑满父容器（350 = 视口宽） |
| `aspect-ratio` + `height:132px` | **282 × 132** | ★★ **宽度被反算**成 132×2.14 —— 没撑满！ |
| `aspect-ratio` + `height:200px` | **428 × 200** | ★★ **横向溢出父容器** 350 |

⇒ **两个后果**：① v10.74 移动端轮播**根本没撑满**（用户其实一直在看 282px 宽的轮播）；
② height 再往上调就直接横向溢出。

★★ 更阴的是：**390 视口下两组比例恰好都 = 2.14**
⇒ 单看「比例是否一致」的判据**照不出来**，只有**守源码**（D17b「移动端不许写死轮播高度」）才拦得住。
**修**：删掉 `@media(max-width:420px)` 里的 `.rk-car{height:132px}`。

## ⑧ 铁律 123–129（本版新增）

123. ★★ **`aspect-ratio` 与确定的 `height` 并存时，`width:auto` 由 `height × ratio` 推出**，
    而不是撑满父容器（实测 390 视口：无 height → **350×164**（撑满）｜`height:132px` → **282×132**（宽被反算）｜
    `height:200px` → **428×200**（**溢出**父容器 350））。
    ⇒ 想「撑满宽度 + 按比例定高」就**只能**写 `aspect-ratio`，**不能**留任何 `height`。
    ★★ 更阴的一面：当父容器比例恰好等于 `--cover-ar` 时，**「比例一致」类判据照不出来**，
    必须**守源码**（不许出现写死高度）才拦得住。
124. ★★ **`every` 在单元素数组上恒真**（v10.75 A7 假绿）。
    凡是「每条都满足 X」的断言，都要先钉住**样本量下限**（`tail.length >= 2`），
    并让测试数据的构造与样本量**同一个常量**（`SRCN = N - 3`）。
125. ★★ **反证不充分有两种病因，症状一样、修法不同**：
    ① **锚点选歪** —— 守 A（tie-break）的断言去测 B（名次对齐）的改动，
    被测语义**对这次破坏免疫**（v10.75 反证 ①）；⇒ 回到**被测语义**重选锚点。
    ② **锚点太宽** —— 子串匹配吃掉别的实现（v10.75 反证 ④ 被「中文名兜底桥」救活）；⇒ **收窄作用域**。
    ★ 与铁律 81「作用域会假红也会假绿」配套：这条讲**反证为什么没红**，那条讲**判据为什么错红/错绿**。
126. ★★ **判源码字符串时必须先剥注释**（v10.75 D17b 假红，**同一坑在同一套件里踩了第二次**）。
    ★ 同族：**锚点判断别用子串**（D13 的 `!/热度/` 咬到 title 提示里的「（本地库热度补位）」）。
127. ★★ **常驻端口跑的是「启动时的代码」**（`server.js` 启动时加载；
    `public/*.html` 才按请求读盘）⇒ 改完 `server.js`/`data/**` **必须重启**，
    否则该端口的响应是**旧逻辑**且几何整体偏移（实测同名接口 top 1768 vs **1501**）。
    ★ 判据不是「有没有 200」，是「**回包里有没有新字段**」（如 `meta.coverBigN`）。
128. ★★ **「结果形态」不能替代「算法语义」**：判「对齐生效」不能只看「有几个机地条目」，
    因为 tie-break 会**独立地**改变这个数字（v10.75 实测：去掉对齐后仍只有 5/11）。
    ⇒ 断言要落在**算法语义**上（榜尾对齐），形态数字只当**辅助观测**。
129. ★★★ **改主源里的「选择器 / 枚举值」时，必须 `grep` 全部 `tools/test-*.js` 里的同一字符串**（v10.75 实测）。
    v10.75 把档位 pill 的 `data-p` 从 `week/month/year` 改成 **`recent/hot/month/year`**：
    静态那套改了，**只在浏览器层跑的 `test-v1074-carousel-live.js` 漏了** ⇒
    它的 `.stage-pill[data-p="week"]` 直接**抛错崩掉整套**（exit 2）。
    ★★ 三点值得记：
    **(a)** 这类漏改**静态层永远照不出来**（静态层不跑选择器，只跑 grep 与纯函数）；
    **(b)** 症状不是「断言红」而是「**异常退出**」，而收尾汇总里「失败 0」**照样成立** ——
      异常退出的那一套**根本没跑完**，它的断言一条都没进统计 ⇒ **「失败 0」≠「全绿」**；
    **(c)** 「改了什么就改它的测试」是**局部**思维，正确动作是**按字符串全量搜**（同一个枚举值
      可能散落在十几套里）。

## ⑩ 本版一句话总结

**用户说的「压缩」，根因不在 CSS 写在哪个属性上，而在「三种源图的原始比例各不相同、
而展示位只有一个比例」** —— 所以本版真正的动作是把**展示位比例对齐到封面原比例（460/215）**，
再用 `coverScore` + 同名提优把**不达标的源图换成达标的**。
而换源那半边，表面是「换个 URL」，实质是**两源规模差 8 倍时如何公平融合** ——
朴素 RRF 会让小源塌陷，必须做**名次相对位置对齐**。
