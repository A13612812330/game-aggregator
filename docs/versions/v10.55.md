# v10.55 · MOD 匹配改「双向子串 + 五道护栏」——修「端游资源整批无关联」

> 基线：v10.54（搜索模糊匹配 + 相关度优先）
> 起因：用户报障「**手机专区的巫师3，但是端游那边无关联**」
> 一句话：MOD 库 8,943 条里 **1,867 条（20.9%）匹配不上端游库**，而 MOD 列表默认只显示已匹配的
> ⇒ 这 1,867 条**在端游资源页一条都不显示**。本次把匹配率 **79.1% → 96.1%**。

## 二、根因与数据

### 2.1 匹配键只有「精确命中」一条路

`matchLib` 一直是 `byName.get(k)`。而：

```
MOD 条目  game = `巫师3：狂猎`                    → 键 `巫师3狂猎`
端游库 xd-120 title = `巫师3：狂猎次世代版/...`    → 段键 `巫师3狂猎次世代版`
```

**是子串关系，但不是同一个键 ⇒ 全漏。** 实测该款 **94 条 MOD 100% `libId` 为空**。

而 `data/mods.js` 第 55/58 行：

```js
const matchedOnly = !(opts.all === '1' || ...);
if (matchedOnly) pool = pool.filter((x) => x.libId);
```

默认 `matchedOnly = true` ⇒ **用户在端游资源页搜「巫师3」得到 0 条**。这就是报障现象。

### 2.2 量级（改前，`node tools/_probe-mod-substr.js`）

| 项 | 实测 |
|---|---|
| MOD/修改器条目 | **8,943** |
| 未匹配 | **1,867（20.9%）** |
| 大头 | `Grand Theft Auto V 传承版` **536** · `荒野大镖客2` 148 · `街头霸王6` 137 · `黑神话:悟空` 127 · **`巫师3：狂猎` 94** · `明末：渊虚之羽` 56 · `英灵神殿 灰烬之地` 49 · `剑与魔法` 44 |

### 2.3 ★ 只做正向包含会漏掉最大的一头

第一版探针只查「库键 ⊃ 查询键」，结果 **GTA V「候选：无」**。真相是反向：

```
条目键 `grandtheftautov传承版`(17)  ⊃  库键 `grandtheftautov`(14)   ← 库键更**短**
```

⇒ 必须**双向**。补上反向之后 536 条一次全中。

### 2.4 ★ 长度比例当主判据会错配

第一版用「短/长 ≥ 0.6」，把 `巫师3：狂猎` 挂到了 **`巫师3狂猎重制版`(8)**——
因为正确的 `巫师3狂猎次世代版`(9) 比例 5/9 = **0.556** 被挡在门外。
⇒ 比例只能当**粗筛**，真正的护栏是**数字一致**。

### 2.5 五道护栏（缺一不可）

| 闸 | 规则 | 只有它能挡的样本 |
|---|---|---|
| **G1** 短键 | 回退层比索引层更严：CJK ≥ 3 / ASCII ≥ 4（索引层是 CJK ≥ 2） | `魔法`(2) vs `剑与魔法`：比例 0.5 / 无数字 / 不降级 |
| **G2** 数字一致 | 查询带数字 ⇒ 候选键必须含（`genNums`，与既有代际护栏同源） | `侏罗纪世界：进化 3` vs `侏罗纪世界：进化`：比例 **0.875** 放行 |
| **G3** 比例粗筛 | 短/长 ≥ **0.5** | `仁王2`(3) vs `仁王2完全版终极收藏版`(10)：0.30 |
| **G4** 变体降级 | 候选含 `虚拟机版 / HYPERVISOR / Demo / 试玩 / 序章 / 体验版 / 先行版` ⇒ **不自动挂** | `怪物猎人：荒野`：唯一候选是 `-虚拟机版`，比例 0.545 放行 |
| **G5** 仲裁 | 剩余多候选 ⇒ 取 **id 序号最小**者，`basis` 标 `substring-ambiguous` | `巫师3：狂猎`：两个候选都是同名变体（5/9 与 5/8 都过 G3） |

★ **G2 实测挡掉的真假阳性**：`HELLDIVERS™ 2` → `Hell Dive`（比例 0.727 放行，数字挡）、
`侏罗纪世界：进化 3` → `侏罗纪世界：进化`。
★ **G4 实测挡掉**：5 个 game 名被挂到「-虚拟机版」（那是另一种内容）。

## 三、验证结果

### 3.1 ★ 基线必须是「旧代码 + 当前库」—— 否则会把数据陈旧算成代码功劳

直接比「磁盘旧 `mods.json` 的 7,076」是**错的**：`mods.json` 比 `games.json` 旧。

| 口径 | 匹配数 | 匹配率 |
|---|---|---|
| 磁盘旧产物（旧代码 + 旧库） | 7,076 | 79.1% |
| **基线：旧代码 + 当前库** | **7,769** | **86.9%** |
| **新代码 + 当前库** | **8,594** | **96.1%** |
| ★ **本次改动真实增量** | **825** | （`substring` 681 + `substring-ambiguous` 144） |

⇒ 原始「7,076 → 8,594 = 1,518」里，**693 条是数据陈旧**、**825 条才是本次代码的功劳**。
**不许把 1,518 当结论写。**

| 样本 | 改前 | 改后 |

## 四、踩到的坑

### 4.1 ★★ `--offline` 重建会**夹带无关变更**（本轮最险的一次）

`tools/fetch-mods.js` 的注释写着「`--offline` 用 `data/_mod-raw.json` 缓存重跑匹配（**改匹配逻辑时用**）」——
看起来正好是这条路的工具。**实测不能这么用**：

| 项 | 旧产物 | `--offline` 重建 |
|---|---|---|
| `linkTotal` | 13,373 | **12,813（少 560）** |
| `links` 数组不一致的条目 | — | **421 条** |
| 条目集合 / `title` | — | 完全一致 |

⇒ 缓存是 **Sep 15** 的快照、旧产物建于 **Oct 10**，重建会把「缓存陈旧」一并算进来。
**条目数与标题都一样，所以不报错、不红，纯静默** —— 正是本项目最怕的那类。
（校验：直接从缓存原始条目跑 `extractLinks` 得 3 条，旧产物是 4 条 ⇒ 缓存内容确实更旧。）

**修法**：新增 `tools/repatch-mods-match.js` —— 只重写 `libId/libTitle/libUrl/matchBasis`
与 `stats.matched/matchedRate/byBasis`，写盘前用**深比较自证**「白名单之外逐字节未变」。
实测：匹配字段变化 1,669 条、**`links` 不一致 = 0**、`linkTotal` 保持 13,373。

### 4.2 ★ 断言必须**判空**，否则打坏后是「崩溃」不是「报红」

`t(matchWithBasis(...).it.id === 'xd-1413', ...)` 这种写法，在回退被删掉时会
**抛 TypeError**，整套件崩掉 ⇒ 反证里「打坏后没变红」根本读不出来（反证 F 分支首跑 **8/10**，
两条报 `(未取到)`）。改成 `!!r.it && r.it.id === ...` 后 **10/10**。
⇒ 铁律 58 的同类：**靶子失效时，报的必须是「红」，不能是「崩」**。

### 4.3 合成样本会把 assertions 写歪

G2 首版样本用了「库里同时有 `侏罗纪世界：进化` 和 `侏罗纪世界：进化3`」——
这时 `matchLib` 走**精确路径**就命中 xd-B，`subMatch` 单独调用反而正确返回 null
⇒ 断言写成「subMatch 应返回 xd-B」**自己就错了**。
修法：样本必须**让精确路径不可用**，并加一条**对照**（无数字时同链路能命中）证明「是 G2 挡的，不是整段失效」。

### 4.4 沙箱不留常驻服务

`PORT=8125 node server.js &` 起的实例会**随 Bash 调用结束被回收** ⇒
`起实例 + curl 验证` 必须放在**同一次调用**里（上一轮记的「8123 是常驻旧进程」在这里的镜像面）。

## 五、架构性收获

1. ★ **「宁缺勿错」要有落点**：G4 让 220 余条（`街头霸王6` 137 / `怪物猎人：荒野` 31 / `EA SPORTS FC 26` 14 …）
   **保持未匹配**，宁可显示「无关联」也不挂到 `-虚拟机版`。这不是漏做，是**有意的取舍**，已写进 `stats`
   可审计（`unmatched = 349`）。
2. ★ **歧义要留痕**：`substring-ambiguous` 是给下一轮看的 —— 全库只有 **3 个 game 名**走仲裁
   （`巫师3：狂猎` / `剑与魔法` / `荒野大镖客`），**全部仲裁正确**。以后要复核只需筛这个字段，不用全量重算。
3. ★ **匹配逻辑仍是一份实现**：`subMatch` 放在 `data/mod-match.js`，`tools/fetch-mods.js` 与
   `tools/fetch-fr.js` 共用；`fetch-fr.js` 未改动即自动获得本次修复（铁律 61）。
4. **「改匹配规则」与「重采集」是两件事**，工具必须分开（§4.1 的工具化落点）。
